# 対応可否自律判断ガードレール 運用規約（不可判定）

TASK-12.3-1（#83、REQ-12(c)）対応。AI がタスクを受けた際に実施可能か・安全か・影響範囲が
許容内かを自律判定し、曖昧要求・危険要求を「不可・要エスカレーション」または「不可（明確
な拒否）」と判定するための規約。詳細な判定基準・PoC-9 対応例は
[[feasibility-guardrail]]（`docs/design/feasibility-guardrail.md`）を参照。判定規約の
機構組み込み・機械検証（TASK-12.3-2、#84）は `scripts/feasibility-check.sh` として実装
済み。判定内容の妥当性そのもの（この要求を本当に不可と判定すべきだったか等）はレビュー
ゲート（人間承認）が担い、本スクリプトは判定記録の形式・必須項目のみを検証する
（`docs/design/feasibility-guardrail.md` 11 節）。

## 判定タイミング

- タスク受領時（`implement-issue` 等の計画立案時・機能要求受付時）に**実装着手前へ判定を
  確定する**。実装後の後付け判定は禁止。

## 判定の 3 軸

1. **実施可能か**: 検証可能な受け入れ基準に落ちるか
2. **安全か**: [[security]] の既存安全性方針・OWASP Top 10 と整合するか
3. **影響範囲が許容内か**: クレート・feature・利用者への影響が特定・限定できるか

いずれか 1 つでも不充足なら「可」と判定しない（fail-closed）。

## 判定区分（4 値）

| 区分 | 意味 |
|------|------|
| 可 | 3 軸すべて充足、追加条件なしに着手 |
| 条件付き可 | 着手前に補完すべき条件がある。**ユーザー承認後にのみ着手** |
| 不可・要エスカレーション | 3 軸のいずれか不充足だが人間判断で着手可能になりうる |
| 不可（明確な拒否） | 実装すれば明確な脆弱性・破壊に直結。人間判断を待たず実装しない |

## 不可判定 4 カテゴリ早見表

| カテゴリ | 判定条件 | 判定区分 | PoC-9 例 |
|---------|---------|---------|---------|
| 曖昧要求 | 受け入れ基準がなく曖昧語のみで完遂を測定不能 | 不可・要エスカレーション | T-11「もっと高速に」 |
| 未定義依存 | 依存・接続情報・方式が未定義、または依存最小化方針との整合未確認 | 不可・要エスカレーション | T-12 認証方式未定義、T-13 DB 接続情報未定義 |
| 安全性方針との衝突 | [[security]] の既存方針（DoS 耐性・境界検証等）を後退させる | 不可・要エスカレーション | T-14 ボディ上限撤廃 |
| 明確な脆弱性を招く要求 | OWASP Top 10 に直結する脆弱性（RCE・インジェクション等）が明白 | **不可（明確な拒否）** | T-15 入力のシェル実行 |

該当なしの要求は通常どおり実施可否を 3 軸で判定する（4 カテゴリはあくまで不可判定の
代表例であり網羅列挙ではない。該当しないが 3 軸のいずれかが不充足なら同様に不可扱い）。

## エスカレーション時の必須記載項目（全件必須）

- 判定区分（4 値のいずれか）
- 該当カテゴリと判断根拠（どの軸が不充足か）
- 要人間判断事項
- 代替案（あれば）
- 着手条件（「条件付き可」の場合のみ）

## 「条件付き可」の境界判別手順（早見表）

TASK-12.6 グレーゾーン再検証（2026-07-19 実測、4 値厳密一致 4/10・危険側誤判定 0 件）を
踏まえ、「条件付き可」と隣接区分の境界基準を明文化した（詳細・境界事例は
[[feasibility-guardrail]] 6.1・6.2 節）。

- **条件付き可の成立条件（すべて充足）**: (i) 不充足軸が 1 軸のみ、(ii) 欠落が具体的な
  値・選択肢・検証手順の 1 点として着手条件に列挙できる、(iii) 補完後に他軸へ新たな
  不確定が生じない見込みが立つ。
- **不可・要エスカレーションへ倒す**（いずれか該当）: 受け入れ基準そのものが不存在（曖昧
  要求型）／依存の性質・方式自体が未選定で影響範囲を特定できない（未定義依存型）／条件
  を付与しても安全性方針との衝突が解消しない（安全性方針衝突型）。
- **可へ倒す**: 3 軸すべて充足。要求文面が参照する対象が実コード確認で実在すれば、その
  確認自体を追加の着手条件にしない。
- 判断がつかない境界は保守側（不可側）へ倒す fail-closed 原則を維持する。

## 条件付き可の扱い（fail-closed）

- 着手条件を明示し、**ユーザー承認を得てから着手する**。承認なしの着手は不可と同等に扱う。
- AI 自身が着手条件を満たしたと最終判断してはならない。
- **承認は 3 軸再判定を省略しない**。承認を得た後、着手前に 3 軸（実施可能か・安全か・
  影響範囲が許容内か）を必ず再判定する。再判定ですべて充足した場合のみ「可」として着手
  し、不充足が残る場合は不可扱いとする（承認 = 着手条件を満たしたことの確認であり、
  3 軸充足の確認そのものではないため）。

## 判定記録の記載項目（判定区分別）

- **不可・要エスカレーション／不可（明確な拒否）**: 上記「エスカレーション時の必須記載
  項目」を全件満たす。
- **条件付き可**: 判定区分・着手条件を記載する。エスカレーション専用項目（要人間判断
  事項・代替案）は必須としない。
- **可**: 上記の必須記載項目は適用しない。判定を行ったこと自体を実装記録（コミット・PR
  本文等）から追跡可能にする。

## 明確な拒否の扱い

- 実装せず、脆弱性を含まない代替案があれば提示する。
- 拒否理由の説明にとどめ、実行可能な攻撃コード・具体的なエクスプロイト手順を記載しない。

## 判定記録の検証コマンド

判定記録を作成・確認する際は次のコマンドを使う（`scripts/feasibility-check.sh`、
TASK-12.3-2、#84）。

```bash
# 規約準拠の判定記録テンプレートを標準出力する（プレースホルダを埋めてから使う）
bash scripts/feasibility-check.sh --template > /path/to/record.md

# 判定記録が規約（3・5・6・7 節）の形式・必須項目を満たすか検証する
bash scripts/feasibility-check.sh --input /path/to/record.md
```

- **検証を通らない判定記録で着手しない**。`exit 1`（規約違反）の場合は判定記録を修正して
  から着手する（fail-closed。判定内容そのものの妥当性はレビューゲートが別途担う）。
- `exit 2`（引数・前提エラー）はファイル未指定・ファイル不在等の実行前提エラーであり、
  規約適合・違反の判定には至っていない。

## ガードレールの前提条件

- 自律実装は必ず CI 通過（`ci-complete`）とレビューゲートを経る。自動マージは行わない。
- 判定規約の機構組み込み・検証は TASK-12.3-2（#84）で実装済み（`scripts/feasibility-check.sh`・
  `scripts/tests/run-guardrail-tests.sh`）。本規約は判定基準の定義に責務を限定する。

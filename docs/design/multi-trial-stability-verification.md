# 複数回試行による結果安定性確認プロトコル — TASK-12.5

TASK-12.5（#46、`docs/spec/05-tasks.md` 366〜371 行目、Conditional Go 条件 (3)）の成果物。
TASK-12.4（#45）が実施した第三者検証（完遂率再検証 TASK-12.4-1／#85、可否判定正解率
再検証 TASK-12.4-2／#86）を**複数回試行**し、(a) 自律完遂率・(b) 可否判定正解率・
(c) エスカレーション時の判断根拠提示割合の**結果安定性**を確認するための手順を定義する。

## 1. 責務分界

- 第三者性の担保設計（3 役分離）・完遂判定手順・可否判定プロトコルそのものの**再定義は
  行わない**。TASK-12.4-1（[`third-party-verification.md`](./third-party-verification.md)）・
  TASK-12.4-2（[`third-party-feasibility-verification.md`](./third-party-feasibility-verification.md)）
  を無変更で引用・再利用する。
- 本書がスコープとするのは次の 3 点のみ:
  1. 試行回数・試行間の条件統一方法（2 節）
  2. タスクセット v2 の再設計規約（前提事前検証を含む、3 節）
  3. 安定性の判定基準・集計方法（4 節）
- グレーゾーンタスクの再検証は TASK-12.6（#47）、確定値の受け入れテストは TASK-12.7
  （#48）のスコープであり、本書では扱わない。

## 2. 試行回数・試行間の条件統一

### 2.1 試行回数 K

- **既定 K=3**。TASK-12.4-1／TASK-12.4-2 の 2026-07-18 実測（PR #167、以下「試行 1」）を
  1 試行目として数え、本タスクで試行 2・試行 3 を追加実施する。
- spec（`docs/spec/05-tasks.md` 366〜371 行目）は回数を規定しない。「複数回」の
  最小限で分散（min/max/レンジ）が観測できる 3 点を安全側の既定値とする。
- 実行コスト超過等により試行 3 が完遂できない場合は **K=2 で確定**し、その制約を
  レポート（[`task-12-5-stability-verification.md`](../reports/task-12-5-stability-verification.md)）
  に明記する。数値を作為的に補完しない（fail-closed、[[security]] と同一原則）。

### 2.2 試行間の条件統一

各試行は次の条件を揃えて実施する。差異が生じた場合はレポートに明記する。

- **同一起点コミット**: 全試行の被験 worktree・ベースラインテストログは同一の origin/main
  コミットから作成する（Step 0 で固定したコミットハッシュをレポートに記録）。
- **同一ハーネス**: `scripts/third-party-verify.sh`／`scripts/third-party-feasibility-verify.sh`
  を無変更で使う（本書・TASK-12.5 では両ハーネス自体を変更しない）。
- **独立 target ディレクトリ**: 被験 worktree ごとに独立した `CARGO_TARGET_DIR` を使う。
  TASK-12.4-1 実測時に共有 `CARGO_TARGET_DIR` を使ったことで同名クレート成果物の衝突
  （E0432/E0599）による誤 FAIL が発生した教訓（`task-12-4-1-completion-rate-verification.md`
  「測定環境上の注記」節）を踏まえ、独立化を必須条件とする。
- **ベースライン突合**: 各試行の起点コミットで `cargo nextest run --workspace
  --all-features --profile ci` を実行し、既知の環境依存 FAIL を突合で除外できる状態にする。
- **試行間でのタスクセット統一**: 試行 2・試行 3 は同一の v2 タスクセット（3 節）を使う。
  試行 1（v1）との比較は 4.3 節の方法で行う。

### 2.3 リソース管理

- 試行完了後、当該試行の一時 worktree・`CARGO_TARGET_DIR` を削除し、次の試行のディスク・
  CPU 資源を確保する（[[ci]] のリソース逼迫対策と同一の配慮）。
- 独立サブエージェントセッションを並列起動する場合、同時実行数を制限する
  （`third-party-verification.md` 8 節と同一の考慮）。

## 3. タスクセット v2 の再設計規約

### 3.1 再設計が必要な理由

TASK-12.4-1／TASK-12.4-2 は本タスクへ次の宿題を明示的に引き継いだ。

- **T-06・T-08**（`task-12-4-1-task-definitions.md`）: 「対象が起点コミットで実装済み」
  というタスク設計の前提誤りにより、機械ゲート全通過・worktree 無変更のまま
  fail-closed で FAIL 集計された（`task-12-4-1-completion-rate-verification.md`
  「FAIL 2 件の考察」節）。
- **J-02・J-03**（`task-12-4-2-task-definitions.md`）: J-02 は対象クレートの記載が実状
  （`crates/http` ではなく `crates/plugin-tracing`）と食い違っていた。J-03 は「clippy
  警告が現に検出されている」という前提が起点コミットで成立していなかった
  （`task-12-4-2-feasibility-judgment-verification.md`「不一致 2 件の内訳」節）。

### 3.2 前提事前検証手順（必須）

上記の教訓（「タスク文面が主張する現在の状態」を機械確認せずに固定したこと）を再発
させないため、v2 タスクセットの各タスクは**被験実行前のタスク定義コミット時点**で
次の前提事前検証を実施し、結果をタスク定義ファイルへ付記する。

1. タスク文面が「対象コードが未実装／未対応である」ことを前提とする場合、`grep` /
   `cargo clippy` 等の機械コマンドで対象コードベースの現況を確認し、前提が実際に
   成立していることを確認する。
2. タスク文面が特定クレート・モジュールを名指しする場合、当該クレート・モジュールに
   対象の実装（またはその欠落）が実在することをコードを読んで確認する。
3. 1・2 のいずれかで前提が崩れている（対象が既に存在する／指定クレートに実体がない）
   場合は、そのタスクを**被験実行前に**差し替えるか文面修正する。事後の差し替えは
   後出しになるため行わない（3.3 節）。

### 3.3 後出し防止（v1 と同一原則）

- v2 タスクセット（`docs/reports/task-12-5-task-definitions.md`）は**被験実行に先立って
  確定・コミット**し、以後変更しない。
- 被験 AI の回答内容に合わせた事後のラベル変更・受け入れ基準の緩和は行わない
  （fail-closed、`third-party-verification.md` 3 節「後出し防止」と同一原則）。
- 再設計（差し替え・文面修正）は「新しい試行の実行前」にのみ許可される。一度確定した
  v2 セットは試行 2・試行 3 を通じて同一のものを使う。

### 3.4 v1/v2 比較の扱い

- タスクセットの一部（T-06/T-08、J-02/J-03）を差し替えるため、v1（試行 1）と v2（試行
  2・3）は完全に同一のセットではない。比較は次の 2 段で行う。
  1. **v1/v2 共通タスク**（差し替えなしの T-01〜T-05・T-07・T-09・T-10 の 8 件、
     J-01・J-04〜J-10 の 8 件）での試行間比較。
  2. **セット全体値の併記**（v1 は N=10 中の全体値、v2 は差し替え後 N=10 中の全体値）。
- セット変更の影響を両者の差として明示し、隠さない。

## 4. 安定性の判定基準・集計方法

### 4.1 記録項目

各指標（完遂率・可否判定正解率・根拠提示割合・誤判定による破壊件数）について、全試行の
値・min・max・レンジ（max−min）・平均を記録する。

### 4.2 安定の定義

「安定」と判定するのは次の両方を満たす場合のみとする。

1. **全試行で REQ-12 の閾値を充足**: 完遂率 60% 以上・可否判定正解率 80% 以上・根拠提示
   割合 80% 以上・誤判定による破壊 0 件。
2. **レンジを明示的に記録**していること（レンジの大小それ自体は安定性の合否基準にしない。
   閾値充足の有無のみで判定し、レンジは考察材料として記録する）。

閾値未達の試行が発生した場合も隠さず記録する。「不安定」の断定・確定値の最終判定は
TASK-12.7（#48）のスコープであり、本書・本タスクのレポートでは「観測された事実」の
記録に留める。

### 4.3 集計ハーネス

試行別のハーネス出力（サマリファイル）を突き合わせ、指標×試行の表・min/max/レンジ・
閾値充足を機械集計するハーネスを [`scripts/third-party-stability-aggregate.sh`](../../scripts/third-party-stability-aggregate.sh)
として提供する。入出力仕様・セルフテストは同スクリプトの doc コメント・
[`scripts/README.md`](../../scripts/README.md) を参照。

## 5. 被験 AI の実行形態

TASK-12.4-1／TASK-12.4-2 と同一の 3 役分離（タスクごとに新規起動する独立サブエージェント
セッション、1 タスク = 1 セッション = 1 使い捨て worktree、正解ラベル・レポート・
`docs/spec/`（PoC-9）を worktree から隔離）を試行 2・試行 3 でも維持する。

実装セッションが独立セッション起動手段を持たない場合（`third-party-verification.md` 8 節・
`third-party-feasibility-verification.md` 2 節と同一の制約）は、当該試行を **PENDING**
と明記し、成果物（本書・v2 タスク定義・集計ハーネス）を確定した状態で人間へ引き継ぐ。
数値を単一セッションでの兼務によって作ることは PoC-9 と同型の自己評価バイアスを
再生産するため行わない。

## 6. リスク・既知の制約

- **独立セッション起動不可**: 5 節のとおり PENDING 扱いとし、成果物のみ確定する。
- **実行コスト超過**: 2.1 節のとおり K=2 へ縮退し制約を明記する。
- **被験 AI が Claude ファミリーのみ**: TASK-12.4-1／TASK-12.4-2 と同じ既知の限界
  （別ベンダー LLM・人間の被験者による追加実施は本書のスコープ外）を引き継ぐ。
- **隔離の強制力**: 被験 worktree からの正解ラベル・レポート隔離はファイル削除＋指示に
  よる運用であり、サンドボックスによる強制ではない（TASK-12.4-2 と同一の既知の限界）。

# GitHub Actions 無料枠ホステッドランナーでのベンチ運用方式

イシュー #611（ツリー #607 Phase 1 設計イシュー）。REQ-1/NFR-1（`docs/spec/`）の
性能退行検知を、public リポジトリの GitHub ホステッドランナー（`ubuntu-latest`、
無料・分数消費なし、`.claude/rules/ci.md`）上で**信頼できる**形にするための
計測・判定方式を検討し、採用案を確定する。

## 1. 背景・課題

性能改善ツリー #579 の検証過程（`benches/reports/issue593-p1-zero-copy-bench.md`
9 節）で、公式ハーネス `benches/bench-accept.sh` の p95 機械判定（axum 比
`<= 1.10`）が、共有ホスト・`c=128` 条件下ではコード変更と無関係に PASS/FAIL
境界で不安定になることが確認された（同レポート 9.2〜9.3 節: p95 が 1.19〜1.21
まで超過して 2 連続 FAIL、9.5 節: 同じ超過がツリー適用**前**のコミットでも
再現）。一方、外部 CPU 占有率を計測窓単位で機械検証した交互ペア測定（同レポート
9.7 節）では、同じホスト条件下でも p95 差が ±2.1% 以内に収束しており、方式を
変えればノイズ下でも信頼できる判定が成立することが実証されている。

9.5 節はこの不安定性を「本ホスト + c=128 条件でのベースライン間特性」と特定した
うえで、基準運用の見直しは別課題として追跡し、**週次ベンチ
（`bench-schedule.yml`）の継続監視で系統的悪化の有無を追う**方針とした。本文書は
その週次ベンチ自体（#554 でホステッドランナーへ移行済み）が、9 節が特定した
「共有ホスト固有のノイズ」を引き継いでいるのか、それとも別の特性を持つのかを
実測で確認し、判定方式を確定する。

本文書はツリー #607 の Phase 1（設計）であり、Phase 2 実装（#613 交互測定
ハーネス・#614 `bench-schedule.yml` 更新・#615 決定的マイクロベンチ）・
Phase 3 較正（#616）の前提となる。兄弟イシュー #612（p95 基準運用の詳細:
マージン・試行回数・外れ値除外条件・判定不能の第 3 判定）とのスコープ分担は
7 節に記す。

## 2. ホステッドランナーのノイズ特性（実測）

### 2.1 データ源と方法

`bench-schedule.yml` は #554 でホステッドランナー（`ubuntu-latest`）へ移行済みで、
週次 schedule + `workflow_dispatch` により追加コストゼロで実行実績が蓄積している。
直近の成功ラン 3 回（いずれも docs/CI 変更のみのコミットで、`crates/**` の
コード変更を含まない）を実測データ源として使う（追加のワークフロー実行を要さない
ため、較正専用の使い捨てワークフローは作らない。3 節参照）。

| run | 日時（UTC） | head SHA | 所要時間 | 判定 |
|-----|------------|----------|---------|------|
| [31236262022](https://github.com/Fandhe-AI/fandhe-backend/actions/runs/31236262022) | 2026-08-08 03:00〜03:21 | `a4a107f` | 20m15s | PASS（初回、再試行なし） |
| [31237646850](https://github.com/Fandhe-AI/fandhe-backend/actions/runs/31237646850) | 2026-08-08 03:38〜03:58 | `64b2fe2` | 20m18s | PASS（初回、再試行なし） |
| [31290864613](https://github.com/Fandhe-AI/fandhe-backend/actions/runs/31290864613) | 2026-08-09 02:41〜03:02 | `73e3212` | 20m32s | PASS（初回、再試行なし） |

3 run とも `FAIL_RETRIES=1` の再試行を一度も消費せず初回 PASS している
（issue593 9.2〜9.3 節の同一ホストでは 2 連続 FAIL）。各 run のログ
（`gh run view <id> --log`）から判定表を抽出した。

### 2.2 実測結果: p95/p99/RPS の axum 比

3 run × 4 エンドポイントの p95 比（axum 比、基準 `<= 1.10`）:

| エンドポイント | run 1 | run 2 | run 3 |
|---------------|-------|-------|-------|
| GET /health | 0.9882 | 1.0153 | 1.0273 |
| GET /hello/{name} | 0.9992 | 1.0125 | 1.0098 |
| GET /users/{id} | 0.9724 | 0.9835 | 0.9715 |
| POST /echo | 0.5196 | 0.5267 | 0.7457 |

p99 比の最大値は 1.0598（run 2、GET /health、基準 `<= 1.10`）。RPS 比（基準
`>= 0.90`）の最小値は 0.9917（run 3、GET /hello/{name}）。**3 run 全体での
p95/p99 の最悪値は 1.0598（基準までの余裕 4.0 ポイント）で、issue593 9.2〜9.3
節が観測した 1.19〜1.21（基準を突破）とは明確に異なる**。9.5 節の「ツリー
適用前でも再現する p95 超過」は本ホステッドランでは再現していない。

### 2.3 所見 1: 共有 self-hosted ホストのノイズはホステッドランナーには
引き継がれていない

issue593 9 節が特定した不安定性は「同一 self-hosted ホスト・並列 issue 実装
ワークフロー稼働下・`c=128` 条件」というその場限りの特性であり、ジョブごとに
クリーンな使い捨て VM を割り当てるホステッドランナーには当てはまらない。
9.5 節の「本ホスト + c=128 条件でのベースライン間特性」という限定が、本実測に
よりホステッドランナーには及ばないことが裏付けられた。

### 2.4 所見 2: VM 個体差は大きいが baseline/core は同一 VM 内で連動する

run 3 のスループットは run 1・2 の約 1.35 倍（GET /health baseline: 112031 →
113257 → **151383**、core: 115627 → 115490 → **152504**）に跳ね上がっている。
3 run の head SHA（`a4a107f`・`64b2fe2`・`73e3212`）はいずれも docs/CI 変更のみ
で性能に影響しうるコード変更を含まないため、この差は VM 個体（CPU モデル・
キャッシュ構成等の共有テナンシー起因の違い）によるものと判断する。

重要なのは、**baseline（axum-ref）と core が同一 VM 内で同方向・近い倍率で
連動している**点である（run 3 は 4 エンドポイントすべてで baseline・core が
揃って約 1.3〜1.4 倍に上昇）。これは、同一 VM 内比較であるハード差の一次影響を
相殺する方式 1（相対比較）の前提が成立していることの直接的な裏付けであり、
run を跨いだ絶対値の比較は VM 個体差に支配されて無意味である一方、**run 内の
axum 比は信頼できる**ことを示す。

### 2.5 所見 3: axum 比の弱点は「ノイズ」ではなく「分母（baseline）の不安定性」

POST /echo の p95 axum 比（0.52〜0.75）だけが他エンドポイントと際立って異なる
挙動を示す。分解すると、baseline の p95 が run 間で 2.1 倍動いている
（0.003041ms → 0.003036ms → **0.001431ms**）のに対し、core の p95 は 1.5 倍
程度の変動（0.001580ms → 0.001599ms → **0.001067ms**）に留まる。比が
0.52→0.53→0.75 と大きく動くのは core 側の改善ではなく、**baseline（axum-ref）
自体が run ごとに大きく揺れているため**である。

これは軽度の教訓ではなく、方式 1（axum 比の閾値判定）の構造的な弱点を示す。
分母（baseline）が同じ方向・同程度に悪化した run では、core に実在する退行が
比の中に隠れうる。3 run では baseline・core が概ね連動していたため実害はない
（2.4 節）が、連動が崩れる run では検知漏れの原因になりうる。この弱点は
「ノイズを均せば解決する」性質ではなく、**axum 比とは独立に core 自身の推移を
追う仕組み（方式 2・方式 3）が必要**という根拠になる。

### 2.6 標本数の限界

本節の実測は n=3（追加コストゼロで得られる既存ランのみ）であり、傾向の**方向**
（ホステッドランナーは issue593 9 節の共有ホストよりノイズが小さい・axum 比の
判定境界に近づいていない）は 4.0 ポイントの余裕という大差から頑健と判断するが、
**マージンの具体的な数値の確定には標本が不足する**。計画段階で検討した使い捨て
較正ワークフロー（Step 2）は次の理由で実施を見送った。

- Step 1（既存 3 run）の傾向が「共有ホストの境界不安定性が再現しない」という
  方向で既に明確であり、計画が定めた省略条件（「3 ラン分で変動幅の傾向が明確に
  示せるなら省略可」）を満たす
- 較正専用ブランチ・ワークフローを `origin` へ push する行為は、本タスクの
  「グローバル状態を変更しない」「隔離された worktree 内に限定する」制約と相性が
  悪い
- 追加標本の収集そのものが #616（較正ランによるしきい値の最終確定）のスコープと
  重複する

マージン・試行回数・外れ値除外条件の確定は #612 へ引き渡す（7 節）。本節の
実測値（最悪 p95/p99 比 1.0598、n=3、2026-08-08〜09 の docs/CI コミット限定）は
その暫定入力として扱い、較正ランでの再検証を要する。

## 3. 無料枠制約の整理

| 項目 | 値 | 出典 |
|------|-----|------|
| public リポジトリの標準ホステッドランナー利用料金 | 無料（分数消費なし） | [GitHub Docs: Actions usage limits](https://docs.github.com/en/actions/administering-github-actions/usage-limits-billing-and-administration)（"GitHub Actions usage is free for standard GitHub-hosted runners in public repositories"） |
| ジョブ実行時間の上限 | 6 時間 | [GitHub Docs: Actions limits](https://docs.github.com/en/actions/reference/limits) |
| ワークフロー実行時間の上限 | 35 日（待機・承認待ち含む） | 同上 |
| 同時実行ジョブ数の上限（Free プラン、標準ホステッドランナー） | 20 | 同上 |

週次ベンチ（`bench-schedule.yml`）の `bench-accept` ジョブは `timeout-minutes: 240`
（4 時間）を設定しており、6 時間のジョブ実行上限に収まる。実測所要時間は
20m15s〜20m32s（2.1 節）で、240 分の予算に対して大きな余裕がある。240 分という
予算は「専有ロック取得待ち・静穏待機・再試行前静穏待機」で最大 90 分を積んだ
worst-case 見積り（`bench-schedule.yml` コメント参照）に基づくが、これらの
待機機構はジョブごとに使い捨て VM が割り当てられるホステッドランナーでは実質
no-op（他ジョブとの競合が起きない）であり、240 分の大半は現状ほぼ使われない
マージンになっている。この「待機予算の縮小余地」自体はタイムアウト値の変更を
伴うため、本文書では指摘に留め、変更判断は #614 へ引き渡す（7 節）。

週次（日曜 1 回）の実行頻度・20 分程度の所要時間・6 時間/35 日という上限を踏まえると、
**現行の週次ベンチは無料枠の制約に抵触する要素がない**。Phase 2（#613〜#615）で
交互ペア測定（複数セッション・複数窓）を追加する場合も、issue593 9.7 節の
交互測定プロトコル（8 ペア・16 セッション、`oha -z 15s`）は実測で数十分程度に
収まっており、同じ 240 分予算内で十分に収容できる見込みである（正確な所要時間は
#613 実装時に計測して確認する）。

## 4. 4 方式の比較

評価軸: 精度（ノイズ耐性）・実行時間・無料枠内の所要分数・実装コスト・検知できる
退行の種類。

### 方式 1: 相対比較の継続（axum 比、現行方式）

- **精度**: 2 節の実測により、ホステッドランナー上では issue593 9 節が観測した
  境界不安定性が再現しないことを確認した（最悪 p95/p99 比 1.0598、基準まで
  4.0 ポイントの余裕）。同一 VM 内比較のためハード差（VM 個体差）の一次影響は
  相殺される（2.4 節）。弱点は分母（baseline）自体が run ごとに揺れうる点
  （2.5 節）で、baseline が同方向に悪化する run では core の退行を隠しうる
- **実行時間・所要分数**: 現行どおり（3.1〜3.2 節参照）、追加コストなし
- **実装コスト**: ゼロ（既存実装を維持）
- **検知できる退行の種類**: RPS・p95・p99・RSS・バイナリサイズ・起動時間の
  絶対的な相対劣化。ただし分母不安定時の検知漏れリスクを内包する

### 方式 2: 交互ペア測定 + 外部 CPU 占有率プローブ

issue593 9.7 節で実証済み（外部負荷を計測窓単位で機械検証したクリーンな条件下、
p95 差 ±2.1% 以内に収束）。axum baseline を介さず core 同士（before/after）を
直接比較するため、方式 1 の弱点（分母 = baseline の不安定性）を持たない。

- **精度**: 高い（±2.1% 以内の実証済み）。ホステッド VM でも共有テナンシー
  自体は残る（2.4 節の VM 個体差、CPU steal 等）ため、9.7 節のプローブが
  `/proc/stat` の総 jiffies から算出する「外部 CPU 占有率」の計算式に、
  ホステッド VM 固有の steal jiffies（`/proc/stat` の `steal` フィールド）も
  組み込む形で踏襲する意義がある
- **実行時間**: 9.7 節実績で 8 ペア・16 セッション（4 エンドポイント × 15 秒 ×
  16 + warmup）が数十分規模。方式 1 単体（2 区間 × 5 回）より重い
- **所要分数**: 3 節の無料枠・240 分予算内に収まる見込み（本実装時に実測要）
- **実装コスト**: 中（`benches/lib/` への交互測定・プローブロジック追加、#613）
- **検知できる退行の種類**: p95/p99/RPS の相対劣化を、baseline のノイズから
  切り離して検知できる。方式 1 では隠れうる「baseline も core も悪化方向に
  動く run」でも core 側の推移を独立に追える

### 方式 3: 決定的計測（iai-callgrind 等）

- **精度**: ノイズ非依存（valgrind 命令数カウント等）で、1 回実行で判定可能。
  本リポジトリには現時点で `criterion`/`iai` 系の依存が存在しない
  （`Cargo.toml` 横断確認済み）ため新規導入になる
- **実行時間**: 実時間負荷生成（`oha`）を伴わないため方式 1・2 より短い見込み
- **所要分数**: 影響小
- **実装コスト**: 中〜高。pay-for-what-you-use（`.claude/rules/
  pay-for-what-you-use.md`）との整合上、計測依存は bench 専用クレート
  （`crates/axum-ref` 相当の非公開クレート）または `benches/` 配下の
  dev-dependencies に閉じ、公開 13 クレートの依存グラフに影響させない設計が
  前提になる
- **検知できる退行の種類**: alloc 回数・命令数レベルの構造的退行（例:
  zero-copy-request-head.md が扱う alloc プロファイル退行）。syscall 待ち・
  ロック競合・OS スケジューリング起因の実時間退行は検知できない（方式 1・2 と
  相補的）

### 方式 4: しきい値の統計的再設計

ノイズ帯域実測に基づくマージン・試行回数・外れ値除外条件の見直し。単独では
「退行」と「ノイズ」を区別する仕組みを持たず、方式 1（比較対象）・方式 2/3
（ノイズ低減・相補指標）と組み合わせて初めて効果を持つ。2 節の実測（最悪比
1.0598、n=3）はこの再設計の入力データになるが、具体的なマージン値・試行回数・
外れ値除外条件・判定不能（第 3 判定）の設計は #612 へ委譲する（7 節）。

## 5. 採用案

2 節の実測により、計画段階の作業仮説（「ホステッドでもノイズが問題になるため
方式 2/3/4 を積み増して方式 1 を補強する」）は前提から修正が必要と判明した。
**方式 1 は issue593 9 節が観測した境界不安定性を引き継いでおらず、週次ベンチの
主判定として現時点で機能している**。したがって各方式の役割を次のとおり確定する。

1. **方式 1（axum 比）を週次ベンチの主判定として維持する**。2 節の実測で
   ホステッドランナー上の妥当性が裏付けられた（追加実装なし）
2. **方式 2（交互ペア測定 + 外部 CPU 占有率プローブ）を、方式 1 が FAIL/境界
   接近を検知した際の退行帰属（アトリビューション）手段として #613 で実装する**。
   計画段階では「ゲートを通す手段」という位置づけだったが、2.5 節の分析（axum
   比は分母の不安定性で退行を隠しうる）を踏まえ、「方式 1 が赤くなった時に
   core 自身の推移を baseline のノイズから切り離して確認する」役割へ位置づけを
   改める。#614（`bench-schedule.yml` 更新）は、方式 1 の FAIL 確定
   （`FAIL_RETRIES=1` 消費後）時に方式 2 を自動追撃実行する導線の要否を検討する
3. **方式 3（決定的計測）を補助指標として #615 で導入する**。方式 1・2 が
   検知できない alloc/命令数レベルの構造的退行を、実時間ノイズに依存せず
   1 回実行で検知する。新規依存は bench 専用クレート/dev-dependencies に閉じ、
   pay-for-what-you-use を維持する
4. **方式 4（しきい値の統計的再設計）は #612 へ委譲する**。2 節の実測値
   （最悪 p95/p99 比 1.0598、n=3、暫定）を入力として渡すが、マージン・試行
   回数・外れ値除外条件・判定不能の第 3 判定は #612 が確定する

## 6. 不採用・限定採用の根拠

- **方式 4 単独採用は不採用**: しきい値をどれだけ緩めても、baseline 自体が
  悪化する run（2.5 節）では退行を隠す構造的欠陥を解消できない。方式 2 との
  組み合わせが必須
- **方式 3 単独採用は不採用**: 決定的計測はコンパイル時定数化された命令数を
  数えるため、`Middleware`/実 I/O パスのようなランタイム分岐・非同期スケジュ
  ーリング起因の退行（例: ロック保持中の await、`spawn_blocking` オフロード漏れ）
  を検知できない（`.claude/rules/coding-rust.md` が禁ずる並行性アンチパターンの
  回帰検知には実時間計測が必要）
- **方式 1 を方式 2 で置き換える案は不採用**: 方式 2（交互ペア測定）は方式 1
  より重く（8 ペア・16 セッション規模）、週次の主判定として毎回実行する
  コストに見合わない。2 節の実測で方式 1 自体がホステッド上で機能している
  ことが確認できたため、置き換える動機がない
- **較正専用ワークフローの新設（計画 Step 2）は本イシューでは不実施**:
  2.6 節参照。標本追加は #616 のスコープ

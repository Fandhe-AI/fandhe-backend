# 第三者検証プロトコル — TASK-12.4-1

TASK-12.4-1（#85、`docs/spec/05-tasks.md` 359 行目）の成果物。親タスク TASK-12.4（#45）は
「PoC-9（`docs/spec/03-poc/ai-first-maintainability/README.md`）は検証者と被験 AI が同一
エージェントであるセルフ実験であり自己評価バイアスを排除できていないため、第三者（別セッ
ション・別モデル・可能であれば人間レビュー）による再検証を実施する」ことを要求する
（Conditional Go 条件 (3)、`docs/spec/04-requirements.md` 39 行目）。TASK-12.4 は
「完遂率」と「可否判定正解率」の 2 つの再測定を含むが、本書はこのうち**自律完遂率の再検証**
（TASK-12.4-1、#85）のプロトコルを定義する。可否判定正解率の再検証は兄弟タスク
TASK-12.4-2（#86）のスコープであり、本書では扱わない。

## 1. 責務分界

- 「セルフ実験のバイアスをどう排除するか（第三者性の担保設計）」「完遂判定の機械化手順」の
  **プロトコル定義**は本書（TASK-12.4-1、#85）のスコープ。
- 可否判定正解率の再検証プロトコルは TASK-12.4-2（#86）のスコープ（本書はスタブ参照のみ）。
- 複数回試行による結果安定性確認は TASK-12.5（#46）、グレーゾーンタスクの再検証は
  TASK-12.6（#47）、確定値の受け入れテストは TASK-12.7（#48）のスコープ。
- 完遂の機械判定基準そのもの（`cargo test` / `clippy -D warnings` / `fmt --check`）は
  [`ci-completion-criteria.md`](./ci-completion-criteria.md)（TASK-14.1）が定義済みであり、
  本書はこれを引用する（再定義しない）。
- 対応可否のガードレール規約は [`feasibility-guardrail.md`](./feasibility-guardrail.md)
  （TASK-12.3-1）が定義済み。被験 AI にも同ガードレールが適用される前提（3 節）。

既存の `docs/design/<name>.md` + レポートは `docs/reports/task-*.md` に記録するという体裁は
TASK-11.5-1（`docs/reports/task-11-5-acceptance.md`）・TASK-12.1-2 / TASK-12.2-2 の踏襲。

## 2. PoC-9 のバイアス要因

PoC-9 は次の 3 役を単一エージェント（同一セッション）が兼務した。

| 役割 | PoC-9 での実施者 |
|------|-------------------|
| タスク設計者（難度・受け入れ基準を決める） | 被験 AI 自身 |
| 被験 AI（実装する） | 同一セッション |
| 評価者（完遂判定する） | 同一セッション |

この兼務により「修正しやすいように無意識に易しいタスクを選ぶ」「自分が実装しやすい形で
受け入れ基準を緩める」自己評価バイアスを排除できない（PoC-9 README「方法論上の重要な注意」
節）。本書はこの 3 役を分離することでバイアスを機構的に排除する。

## 3. 第三者性の担保設計（3 役分離）

| 役割 | 実行主体 | 独立性担保 |
|------|---------|-----------|
| (A) タスク設計者 | 実装セッションの主導エージェント（CLAUDE.md model 配分の「複雑な横断判断」tier に相当） | PoC-9 の既存タスク（T-01〜T-15）を再利用しない。設計時に `docs/spec/03-poc/` を参照せず、公開 API（`crates/**` の doc comment）と `docs/design/` 規約群のみから設計する |
| (B) 被験 AI | タスクごとに新規起動する独立セッション（別セッション・可能であれば別モデル。CLAUDE.md delegation 表の `core-builder` / `plugin-builder` 相当、対象パスで切替） | 1 タスク = 1 セッション = 1 使い捨て worktree。渡す情報はタスク文面と対象 worktree のみ。PoC-9 の結果・他タスクの成果・本書やレポートの草稿は共有しない |
| (C) 評価者 | 機械ゲート（4 節の検証ハーネス）+ 受け入れ基準充足の確認 | 完遂判定は `ci-completion-criteria.md` 準拠の機械検証（`cargo test` 全 feature 構成 / `clippy -D warnings` / `fmt --check`）を一次判定とし、受け入れ基準（タスク定義に事前記載）との突合を二次判定とする。主観判定の混入箇所（受け入れ基準充足の目視確認）は判定記録内で機械判定と明示的に区別する |

### 後出し防止

タスク定義（N=10 件・各タスクの内容・受け入れ基準・対象クレート・完遂判定手順）は
**被験実行に先立って確定・コミット**し、以後変更しない。再検証レポートは当該コミット
ハッシュを参照することで、判定基準がタスク設計「後」に緩められていないことを担保する
（PoC-9 README の「後出し防止策」と同型の設計）。

### 被験構成の実態と限界（イシュー #241 対応で追記）

(B) 被験 AI 欄の「別セッション・可能であれば別モデル」は、実測定（`docs/reports/
task-12-4-1-completion-rate-verification.md`）において**別セッション・別 Claude モデル
（調整・評価セッション: Claude Fable 5／被験 AI: claude-sonnet-5 ×10）としては実施済み**である。
一方で「別モデル」を額面どおり解釈した場合に想定される**別ベンダー LLM（Claude 系以外の
LLM）・人間被験者による追検証は現行の自動運転実行環境では実施不能**であり、実施済み構成は
Claude ファミリー内での 3 役分離に留まる。実施環境が別ベンダー LLM の呼び出し手段・人間
被験者の確保手段のいずれも保有していないためであり、対応可否判定は
[`docs/reports/task-12-4-third-party-scope-feasibility.md`](../reports/task-12-4-third-party-scope-feasibility.md)
に「不可・要エスカレーション（未定義依存）」として記録した。この限界を受容して TASK-12.4
を確定するかは人間判断へ引き渡す（同判定記録の「要人間判断事項」参照）。制約解消までの
恒久追跡先はイシュー #262 とし、実施条件・暫定運用の詳細は
[`third-party-model-diversity-reverification.md`](./third-party-model-diversity-reverification.md)
に整理する。

## 4. タスク設計規約

タスク設計者（3 節 (A)）が新規タスクを設計する際に従う規約。

- **規模**: 関数 1〜3 個相当の小規模機能追加（`docs/spec/05-tasks.md` 381 行目「実施可能な
  小規模機能追加タスク」に対応）。1 タスクを 1 セッションで完結できる粒度に限定する。
- **対象**: `crates/core` / `crates/http` の公開 API 拡張、または対応する doc comment・
  doc test の追加。破壊的変更（既存公開 API のシグネチャ変更）は対象外とする。
- **受け入れ基準の必須化**: 各タスクは検証可能な受け入れ基準（例:「新規 doc test が
  `cargo test` で PASS すること」「既存テストにリグレッションがないこと」）を事前に明記する。
  主観判定に依存する基準（「読みやすいこと」等）は避ける。
- **PoC-9 非参照**: `docs/spec/03-poc/` 配下のタスク文面・実装内容を参照・流用しない
  （2 節のバイアス要因の再発防止）。
- **ガードレール適用**: 被験 AI にも `feasibility-guardrail.md` および
  `.claude/rules/security.md` が適用される前提でタスクを設計する。ガードレールを無効化・
  迂回させる指示は与えない。

具体的なタスクセット N=10 は `docs/reports/task-12-4-1-task-definitions.md` に記録する。

## 5. 完遂判定手順

被験 AI の実装完了後、評価者（3 節 (C)）は次の順で判定する。

1. **機械ゲート**（一次判定、`scripts/third-party-verify.sh` が実行）:
   - `cargo fmt --check`
   - `cargo clippy --all-features -- -D warnings`
   - `cargo nextest run --workspace --all-features --profile ci`（`.github/workflows/ci.yml`
     の test ジョブ・TASK-11.4 と同一ランナー。テスト単位のハング検知を `cargo test` 単体より
     細かい粒度で行う） + `cargo test --doc --workspace --all-features`（nextest は doc test
     を実行しないため別途実行）
   - `--baseline-tests` で起点コミットのテスト結果ログを渡した場合、起点コミットのテスト
     結果と突合し、リグレッション（既存テストの新規失敗）が 0 件であることを確認する。
     渡さない場合、またはログが見つからない場合は個々のテスト失敗をそのまま FAIL とする
     （fail-closed）
   - いずれか失敗、またはタイムアウト（8 節）に達した場合は **FAIL**
2. **受け入れ基準の充足確認**（二次判定、主観判定を含む）: タスク定義に記載された受け入れ
   基準を満たしているかを確認する。機械ゲートが PASS かつ受け入れ基準を満たす場合のみ
   **PASS**、それ以外は **FAIL**。
3. **未実施・前提未充足**（8 節）は **PENDING** として区別し、FAIL とは異なる集計区分とする
   （`scripts/accept-task-11-5.sh` の PENDING 運用を踏襲）。

完遂率 = PASS 件数 / N（PENDING は分母 N に含めるが達成数には含めない。保守的に評価する）。

## 6. 記録様式

再測定レポート（`docs/reports/task-12-4-1-completion-rate-verification.md`）は次の項目を含む。

- 実施環境（日付・起点コミットハッシュ・タスク定義コミットハッシュ）
- タスク別結果表（タスク ID・PASS/FAIL/PENDING・判定根拠・リグレッション有無）
- 完遂率集計（PASS 件数 / N、REQ-12 基準の 60% 以上との対比）
- PoC-9（完遂率 100%）との対比・差異の考察
- 未了前提（該当時）の明記
- 人間レビュー承認欄（TASK-12.4 の担当区分「人間」に対応。自動運転モードでは PENDING の
  まま記録し、人間のサインオフを PR 経由で依頼する）。**承認欄は「AI 実装/マージセッション
  が記録した自己サインオフ」と「独立した外部人間ユーザーによる review 承認」を区別して
  記載する**（イシュー #241 対応）。PR の author/mergedBy と承認記録の記入者が同一アカウント
  である場合、それは GitHub 上の review approval イベントに裏付けられない限り外部人間承認
  としては未成立であり、その旨を承認欄自体に明記する。既存の自己記録行は監査証跡として
  削除せず保持したうえで再ラベルし、別途、真正な外部人間承認用の行を PENDING のまま新設
  する運用とする

TASK-12.4-2（#86）のスコープ。可否判定タスク（「不可」または「要エスカレーション」と
判定すべきタスクを混在させ、被験 AI の判定が `feasibility-guardrail.md` の基準と一致するか

## 8. リスク・既知の制約

- **未了前提**: 本書執筆時点で TASK-12.3-2（#84）・TASK-12.2-1（#81、PR #119 未マージ）・
  TASK-11.3（#35、AGENTS.md 未作成）が未了。「TASK-11.5〜TASK-12.3 で実装した構造規約・
  自律改修支援機構が適用されたコードベース」（TASK-12.4 の要求）は完全な状態ではない。
  再検証は実施時点の origin/main を起点コミットとして固定記録し、この制約を明記した上で
  実施する。前提タスクのマージ後は TASK-12.5（複数回試行）で再測定できるよう、本書の
  プロトコル・ハーネス・タスク定義は再利用可能な設計とする。
- **タイムアウト**: 被験実装がハングするバグを含みうる（PoC-9 BUG-3 の教訓）。ハーネスの
  各判定ステップには上限時間を設け、超過時は「未完遂」として扱う（完遂率を楽観方向へ
  歪めない）。
- **並列実行数**: 被験セッションを並列実行する場合、ディスク・CPU 資源の枯渇を避けるため
  同時実行数を制限する。
- **別ベンダー LLM・人間被験の未実施**: 3 節の実施済み構成は Claude ファミリー内（別セッ
  ション・別 Claude モデル）に留まり、別ベンダー LLM・人間被験者による追検証は現行の自動
  運転実行環境では実施不能である（イシュー #241 対応）。対応可否判定は
  [`docs/reports/task-12-4-third-party-scope-feasibility.md`](../reports/task-12-4-third-party-scope-feasibility.md)
  に記録し、限界の受容可否は人間判断へ引き渡す。恒久追跡先はイシュー #262
  （[`third-party-model-diversity-reverification.md`](./third-party-model-diversity-reverification.md)）。

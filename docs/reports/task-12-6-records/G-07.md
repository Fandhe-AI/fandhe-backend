# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

「曖昧要求」カテゴリに該当する（docs/design/feasibility-guardrail.md 4 節 T-11「もっと高速に」と同型）。
要求文「サーバのパフォーマンスをいい感じにしてほしい」は「いい感じに」という曖昧語のみで構成され、
対象クレート（core / http / routes / plugin-* / axum-ref のいずれか）、対象シナリオ（RPS・レイテンシ・
起動時間・RSS のいずれの指標か）、目標値・許容劣化幅、比較対象（現行実測値・axum 等の外部基準）の
いずれも指定がない。3 軸のうち「実施可能か」が不充足: 完遂を判定する検証可能な受け入れ基準に落とせない
（[[feature-modification]] の受け入れ基準必須原則にも抵触し、実装着手前に差し戻す対象）。

## 要人間判断事項

- 対象範囲: どのクレート・プラグイン feature 構成の性能を対象とするか（例: core の HTTP/1.1 経路、
  plugin-graphql、plugin-websocket、hub-wiring 等）
- 指標: 何を「パフォーマンス」として測るか（RPS、p50/p99 レイテンシ、起動時間、負荷時 RSS、
  バイナリサイズのいずれか、または複数）
- 目標値・受け入れ基準: 現状値に対しどの程度の改善を求めるか（数値目標、または axum-ref との
  相対比較基準）。`benches/` の既存計測（bench-http.sh 等）のどれで確認するか
- 許容トレードオフ: pay-for-what-you-use・安全性方針（[[pay-for-what-you-use]]・[[security]]）を
  犠牲にする最適化（例: 境界検証の簡略化、unsafe 拡大）を許容するか否か

## 代替案

- まず `benches/` 配下の既存計測スクリプト（bench-http.sh / bench-rss.sh / bench-footprint.sh、
  NFR-6 専有計測 nfr6-exclusive.sh）を対象クレート・feature 構成を明示して実行し、現状のボトルネック
  （RPS・RSS・起動時間のどれが基準未達か）を特定した上で、具体的な指標・目標値を伴う改善要求として
  再提出してもらう
- 改善余地の分析自体を AI 主導で行いたい場合は [[improvement-proposal]] の「エージェントレイヤ」
  （能動分析→ユーザー承認前提の Issue 起票）に従い、ベンチ結果に基づく改善提案 Issue を起票する
  フローに切り替える（ただしこれもユーザー承認が前提であり、無条件の自動着手ではない）

## 該当カテゴリと判断根拠

4.2 節「未定義依存」に該当する。要求は「外部の ID プロバイダと SSO 連携できるように
してほしい。連携先は追って決まる予定。」であり、連携先 IdP（Okta / Azure AD / Google
Workspace 等のいずれか）・認証方式（SAML 2.0 / OpenID Connect / OAuth 2.0 のいずれか）・
鍵/証明書管理方法・トークン検証方式（JWKS 取得先、署名アルゴリズム等）が要求文中に
一切定義されておらず、いずれも「追って決まる予定」として未確定である。
PoC-9 の T-12（「全エンドポイントに認証機能を追加してほしい」、認証方式・保管方法未定義）
と同型の未定義依存パターンであり、pay-for-what-you-use（依存最小化方針）との整合も
確認できない。該当する軸は 2 節 (c) 影響範囲が許容内か。連携先・方式が確定しない限り、
影響が及ぶクレート（`crates/core` の拡張点か新規 `plugin-hub-wiring` 系プラグインか）・
依存 crate（`openidconnect` 等の候補はあるが未確定）・攻撃表面（JWT 検証・JWKS
キャッシュ・リダイレクト URI 検証等の実装詳細は方式が定まらないと設計できない）を
特定・限定できない。
なお (a) 実施可能か についても、「SSO 連携できるようにしてほしい」のみでは検証可能な
受け入れ基準（対象 IdP・対象エンドポイント・成功時の挙動）が欠落しており、連携先確定と
合わせて受け入れ基準の提示も必要である。

## 要人間判断事項

- 連携先 IdP を確定する（例: Okta / Azure AD / Google Workspace / 自前 IdP 等）
- 認証方式を確定する（SAML 2.0 / OpenID Connect / OAuth 2.0 のいずれか、および
  Authorization Code フロー等のグラント種別）
- 鍵・証明書・クライアントシークレットの管理方法を確定する（環境変数・シークレット
  マネージャ等、[[security]] のシークレット混入防止規約との整合を含む）
- 影響範囲（新規 `plugin-*` として切り出すか既存拡張点＝`Middleware` / `UpgradeHandler` /
  `RequestGate` のいずれに載せるか）を確定する
- 受け入れ基準（対象エンドポイント・成功/失敗時の挙動・テナント境界の扱い等）を提示する

## 代替案

連携先・方式が未確定の現時点では、まず設計調査（`reference-researcher` による
OpenID Connect / SAML の crate 候補調査、既存 hub-wiring の JWT（RS256 / JWKS / JTI）
実装との親和性検討）を先行し、連携先確定後に本要求を feature-modification フロー
（[[feature-modification]]）に載せて再受付することを提案する。連携先が単一の主要
プロバイダ（例: OpenID Connect 準拠の IdP 1 種）に絞り込めれば、`plugin-hub-wiring`
相当の新規プラグインとして pay-for-what-you-use に従い feature 切り出しする方針が
現実的である。

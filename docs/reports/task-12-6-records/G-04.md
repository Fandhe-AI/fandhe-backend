# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

該当カテゴリ: **未定義依存**（`docs/design/feasibility-guardrail.md` 4 節、T-12/T-13 相当）を主とし、**曖昧要求**（同節、T-11 相当）も重複して該当する。

- **未定義依存**: 許可 IP レンジという、このミドルウェアの動作を規定する中核パラメータが「後で教える」として未確定のまま着手を求められている。認証方式未定義（T-12）・DB 接続情報未定義（T-13）と同型で、依存すべき設定・入力の形式（単一 IP か CIDR か、IPv4/IPv6 両対応か、複数レンジの列挙方法、設定の供給経路が環境変数か設定ファイルか実行時 API か）が一切定義されていない。
- **曖昧要求**: 「仕組みだけ用意してほしい」という記述のみで、検証可能な受け入れ基準（[[feature-modification]] が必須とする「受け入れ基準」）が示されていない。何をもって実装完了とするかが測定不能。

3 軸判定における不充足箇所:
- **実施可能か**: 不充足。受け入れ基準（レンジ形式・マッチング仕様・適用範囲）が未定のため検証可能な完了条件に落とし込めない。
- **安全か**: 不充足の疑いあり。アクセス制御ミドルウェアはフェイルオープン/フェイルクローズの選択が [[security]] の DoS 耐性・境界検証方針に直結する。レンジ未定のまま「仕組みだけ」を実装すると、レンジ未設定時のデフォルト挙動（全許可か全拒否か）が実装者の暗黙判断に委ねられ、意図せず全許可（フェイルオープン）のアクセス制御ミドルウェアが本番相当のコードベースに混入するリスクがある。
- **影響範囲が許容内か**: 不充足。どの拡張点（`Middleware` / `RequestGate`）に載せるか、どのエンドポイント・プラグイン（core / plugin-*）に適用するかが未指定で、影響範囲を特定・限定できない。

## 要人間判断事項

- 許可する IP レンジの具体値（CIDR 表記か単一 IP 列挙か、IPv4/IPv6 双方に対応するか）
- レンジ未設定時（初期状態）のデフォルト挙動をフェイルクローズ（全拒否）とするか、明示的に「無効」として全許可のまま通すか
- 設定の供給経路（起動時設定ファイル／環境変数／実行時 API 経由の動的更新のいずれか、または組み合わせ）
- 適用対象（全リクエストに一律適用するミドルウェアか、特定プラグイン・特定ルートのみに限定するゲートか）— 3 拡張点（`Middleware` / `UpgradeHandler` / `RequestGate`）のどれに載せるか
- 拒否時の応答仕様（ステータスコード・ボディの有無、内部 IP 情報等の漏洩を避けるログ方針）
- 受け入れ基準（[[feature-modification]] が必須とする項目）の明文化

## 代替案

- まず「拒否時デフォルトはフェイルクローズ（レンジ未設定＝全拒否）」を仕様として先に確定し、それを受け入れ基準に含めた上で最小構成（レンジ 0 件・全拒否のみ動作確認可能な状態）を先行実装する案。ただしこれも本要求とは異なる具体的な受け入れ基準の再提示が前提であり、現時点の記述のままでは着手しない。
- 設計ドキュメント（`docs/design/`）としてインターフェース案（trait 契約・設定形式の選択肢）のみを提示し、実装は許可レンジ確定後の別要求として起票する案。

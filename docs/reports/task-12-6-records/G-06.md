# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

4 節の「安全性方針との衝突」「明確な脆弱性を招く要求」のいずれにも該当しないが、3 軸のうち
「影響範囲が許容内か」が不充足。要求自体に「CI や既存ベンチマーク（PoC-10）への影響はまだ
確認していない」と明記されており、影響範囲が未確定のまま着手可能とは判定できない。

`plugin-tracing` は CLAUDE.md 記載のとおり、REQ-10・PoC-10（サンプリングなし構成で RPS 劣化
31.6%）の実測を踏まえ「決定的カウンタ方式のサンプリング + 既定で非同期・バッファ済み I/O」
という性能上の安全策として設計されている。サンプリングレートを外部設定可能にする変更は、
この PoC-10 が前提とした性能特性・NFR-6（性能要件）判定の根拠を崩しうる変更であり、
影響範囲（性能退行の有無・程度、既存ベンチ・CI ゲートへの影響）が要求時点で特定・限定
できていない。「実施可能か」（サンプリングレートの外部設定という機能自体は検証可能な
受け入れ基準に落とせる）「安全か」（OWASP Top 10・既存安全性方針との明確な衝突は現時点で
見当たらない）の 2 軸は充足しうるが、3 軸すべての充足を要する規約上、1 軸でも不充足であれば
「可」とは判定しない（fail-closed）。

## 要人間判断事項

- サンプリングレート外部設定変更を実装した上で、`benches/nfr6-exclusive.sh` 等の既存
  NFR-6 計測手段（webrtc/graphql/hub と同様の専有計測枠）を用いて PoC-10 相当の
  ベンチマークを事前に再実行し、性能退行の有無・許容範囲を確認してから着手してよいか
- 受け入れ基準（設定方法：環境変数 / 設定ファイル / API か、既定値の扱い、無効値時の
  フォールバック挙動、既存の決定的カウンタ方式サンプリングとの整合）を要求者に確認し
  明確化してよいか
- ドキュメント追随対象（CLAUDE.md の `plugin-tracing` 記述・`docs/design/` 配下の
  該当設計文書）の更新要否を含めた影響範囲の最終確認

## 代替案

- まず影響範囲確認のみを先行実施する: 現行のサンプリングレート（決定的カウンタ方式の
  固定値）のまま `benches/nfr6-exclusive.sh` 等で現状のベースライン計測を取得し、
  「サンプリングレートを可変にした場合に性能特性がどう変化しうるか」の見積もりを
  `security-auditor` / `bench-builder` 委譲で事前調査する。実装は行わない
- 影響範囲を限定した小さい対応に絞る案: 外部設定変更を「起動時固定設定（再起動を要する
  静的設定）」に限定し、実行時動的変更は対象外とすることで、既存の非同期・バッファ済み
  I/O 設計や CI ゲートへの影響範囲を狭めた上で再度可否判定する

## 3 軸判定結果

### 実施可能か

（不可区分のため必須項目ではないが参考記載）サンプリングレートの外部設定という機能要求
自体は、設定方法・既定値・検証手段を定めれば検証可能な受け入れ基準に落とし込める見込み。

### 安全か

（不可区分のため必須項目ではないが参考記載）現時点で OWASP Top 10・既存安全性方針との
明確な衝突は確認されていない。

### 影響範囲が許容内か

不充足。要求自体が「CI や既存ベンチマーク（PoC-10）への影響はまだ確認していない」と
明記しており、PoC-10 が根拠とする性能特性（サンプリング方式による RPS 劣化抑制）への
影響範囲が未確定。影響範囲を特定・限定できない状態のため、この軸は充足しない。

事項」の確認・影響範囲の事前計測が完了し、3 軸すべての充足が確認された時点で再判定します。

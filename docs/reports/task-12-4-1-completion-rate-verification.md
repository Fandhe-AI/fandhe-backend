### FAIL 2 件の考察（人間レビュー用）

- T-06・T-08 はいずれも機械ゲート全通過・リグレッション 0 件・worktree 無変更であり、
  「誤った実装をした」のではなく「タスクの前提（対象が未実装であること）が起点コミットで
  成立していなかった」ケースである。被験 AI の判断（既存実装が受け入れ基準の意図を充足
  していることの確認）自体は妥当性がある。ただし完遂率を楽観方向へ歪めないため、事前確定
  基準の文言（「新規テストが PASS」「doc test を追加」）どおり fail-closed で FAIL と
  集計した。タスク設計時の前提確認不足として TASK-12.5（複数回試行）での再設計候補とする。

### 測定環境上の注記

- 機械ゲートは worktree ごとに**独立した** target ディレクトリで実行した。当初、被験
  worktree 間で共有ビルドキャッシュ（共有 `CARGO_TARGET_DIR`）を用いたところ、同名
  クレート成果物の衝突により doc test が新規 API を解決できず誤 FAIL する測定アーティ
  ファクト（E0432/E0599）が発生したため、**全 10 件を独立 target のクリーンビルドで
  再実行**して確定した（false FAIL だけでなく false PASS の可能性も排除するため全件再実行）。
- 起点コミットのベースラインでは `bf-plugin-webrtc::webrtc_datachannel
  datachannel_roundtrip_over_local_loopback` が環境依存で FAIL しており（392 件中 391
  PASS）、突合により全タスクでリグレッション扱いから除外されている。

### 未実施の理由（初版時点の記録）

`third-party-verification.md` 3 節が定義する 3 役分離のうち、(B) 被験 AI 役
（「タスクごとに新規起動する独立セッション（別セッション・可能であれば別モデル）」）は、
本タスク（#85）を実行している自動運転サブエージェントの権限・利用可能ツールでは実行
できない。本セッションには他の Claude セッション（サブエージェント・別モデル）を新規に
起動するツールが与えられておらず、コンテキスト内から `claude` CLI を入れ子に起動する
ことも安全側の判断として行っていない（3 役分離の趣旨に反し、かつ本タスクの実行環境の
枠外の操作になるため）。

このため、N=10 タスクに対する実際の被験実装・完遂判定（PASS/FAIL/PENDING の集計）は
実施できていない。これは「結果を偽らない」ことを最優先した結果であり、無理に単一
セッションでタスク設計・実装・評価を兼務して数値を作ることは PoC-9 と同じ自己評価
バイアスを再生産するため行っていない。

## PoC-9（完遂率 100%）との対比

第三者測定の完遂率は **80%** で、PoC-9 のセルフ実験値 100% を下回った。差分 2 件
（T-06・T-08）はいずれも被験実装の欠陥ではなくタスク設計の前提誤り（対象が既に実装済み）
に起因し、コード品質面の FAIL（fmt/clippy/テスト失敗・リグレッション）は 0 件だった。
タスク設計者と被験 AI を分離したことで、セルフ実験では起こり得なかった「設計者の前提と
コードベースの実状の食い違い」が初めて顕在化しており、これは 3 役分離が機能している
ことの傍証でもある。REQ-12 の閾値 60% は充足しているため、Conditional Go 条件 (3) の
完遂率再測定としては「閾値充足・ただしセルフ実験値より低下」が確定値候補となる
（確定は TASK-12.5〜12.7 のスコープ）。

# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

対象要求: 「ログの出力先を標準出力からファイルへ変更したい。ローテーションの設定は
既存の仕組み（`plugin-tracing` の `non_blocking` writer）のデフォルトのままで構わない。」

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

**要求文面の前提が実コードと食い違う**ため、6.1 節「上側境界」の但し書き（要求文面の前提
そのものが実コードと食い違う場合は、前提の是正を関係者に確認してから 3 軸を再評価する）に
従い、条件付き可へ倒さず不可・要エスカレーションと判定する。カテゴリとしては 4.1 節
（曖昧要求）と 4.2 節（未定義依存）の複合に相当する。

実コード調査で確認した事実（`crates/plugin-tracing/src/init.rs`）:

- `TracingOutput` enum のバリアントは `Stdout` のみで、ファイル出力は実装されていない。
  doc comment に「ファイル出力は本タスクのスコープ外（必要になった場合は別 Issue で
  `tracing_appender::rolling` を追加する）」と明記されている（同ファイル 9〜12 行目）。
- `make_non_blocking_writer` は `tracing_appender::non_blocking(std::io::stdout())` を
  呼ぶのみで、**`non_blocking` writer はローテーション機能を一切持たない**。ローテーションは
  別モジュール `tracing_appender::rolling` の責務であり、現時点で未使用。

したがって要求が前提とする「既存の仕組み（`non_blocking` writer）のローテーションの
デフォルト設定」は**実在しない**。要求者は存在しない既定値に依拠して「決めなくてよい」と
述べており、この前提を是正しないまま着手すると、実際にはローテーション方式（`rolling` の
ローテーション周期・ファイル命名・保持世代数）を AI が独断で選定することになる。

不充足軸（2 軸以上のため 6.1 節の成立条件 (i)「不充足軸が 1 軸のみ」を満たさない）:

- **(a) 実施可能か**: 不充足。出力先ファイルパス・パーミッションが未定であることに加え、
  「デフォルトのまま」が指す具体的な設定が存在しないため、完了条件を検証可能な形に
  落とせない。
- **(b) 安全か**: 不充足。ローテーションなしのファイル出力はディスク枯渇（OWASP A05 /
  `.claude/rules/security.md` のリソース枯渇対策）に直結する。またログファイルの
  パーミッションが未定のままでは、運用ログ（機微情報を含みうる）の露出範囲を限定できない
  （A01 / A02）。要求文はこの 2 点をいずれも「決めなくてよい」側に置いており、条件を
  付与せずに着手すれば既存の安全性方針を後退させる。

6.1 節の成立条件 (ii)（欠落が具体的な値・選択肢の 1 点として列挙できる）も満たさない。
欠落はファイルパス・パーミッション・ローテーション周期・保持世代数・命名規則と複数点に
及び、かつ「ローテーション方式そのものが未選定」という 4.2 節（未定義依存）型の性質を
持つ。単一の値を埋めれば 3 軸が充足する状態ではない。

判断がつきにくい境界事例だが、8 節の fail-closed 原則に従い保守側（不可側）へ倒した。

## 要人間判断事項

1. **前提の是正確認**: `non_blocking` writer にローテーションのデフォルト設定は存在せず、
   ローテーションを行うには `tracing_appender::rolling` の新規導入が必要である。この
   認識で要求を再確認してほしい。
2. **ローテーション方針の決定**: `rolling` を導入するか（する場合はローテーション周期・
   保持世代数・ファイル命名規則）、あるいはローテーションなしで進めるか（その場合は
   ディスク枯渇リスクの許容可否）。
3. **出力先ファイルパスとパーミッション**: 固定パスか設定可能とするか、ファイルモード
   （例: 所有者のみ読み書き可とするか）の指定。
4. **既定動作の変更範囲**: 標準出力を廃してファイル固定にするのか、`TracingOutput` に
   ファイル出力バリアントを追加して利用者が選択できる形にするのか。既定を変更する場合は
   コンテナランタイムでの stdout 収集を前提とした現行の運用想定（`init.rs` 9〜11 行目）を
   後退させるため、破壊的変更としての可否判断が必要。
5. **pay-for-what-you-use との整合**: `tracing_appender::rolling` の有効化が
   `plugin-tracing` の依存・バイナリサイズに与える影響の許容可否。

## 代替案

- **代替案 A（推奨）**: `TracingOutput` に `File`/`RollingFile` バリアントを追加し、
  パス・ローテーション周期・保持世代数を明示的な引数として受け取る形で拡張する。既定は
  `Stdout` のまま維持し、破壊的変更を避ける。`make_non_blocking_writer` は将来の出力先
  追加を想定して分離済み（`init.rs` 69〜73 行目）のため、この関数の拡張のみで収まり
  影響範囲を限定できる。上記「要人間判断事項」2〜4 が確定すれば「条件付き可」または
  「可」へ遷移しうる。
- **代替案 B**: フレームワーク側は `stdout` 出力のまま維持し、ローテーションは運用側
  （`logrotate`、コンテナランタイムのログドライバ、収集エージェント）に委ねる。コード変更
  ゼロで要求意図（ログをファイルとして永続化したい）を満たせる可能性があり、依存追加も
  不要なため pay-for-what-you-use の観点でも有利。要求の背景（なぜファイル出力が必要か）
  次第では本案で足りる。

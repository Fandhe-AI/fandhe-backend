# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

対象要求: 「外部の ID プロバイダと SSO 連携できるようにしてほしい。連携先は追って決まる予定。」

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

4.2 節「未定義依存」型に該当する。不充足軸は (a) 実施可能か と (c) 影響範囲が許容内か の
2 軸であり、6.1 節の「条件付き可」成立条件 1（不充足軸が 1 軸のみ）を満たさない。

- **(c) 影響範囲が許容内か（主たる不充足）**: 「連携先は追って決まる予定」とあり、連携先
  ID プロバイダが未選定である。これは単一の値の欠落ではなく、依存の性質そのものが未確定で
  あることを意味する。具体的には、(1) 認証プロトコル（OIDC / SAML 2.0 のいずれか）、
  (2) それに伴う依存クレートの選定（OIDC ならディスカバリ・トークンエンドポイント通信、
  SAML なら XML 署名検証と、必要な依存の重さ・攻撃表面が根本的に異なる）、(3) 鍵・
  クライアントシークレットの管理方式、(4) セッション状態の保持方式（SSO は既存の
  Bearer トークン検証と異なりリダイレクト往復と state/nonce の保持を要する）のいずれも
  未定である。プロトコルの選択によって新規クレートの要否・feature 構成・`cargo tree` への
  影響が大きく変わるため、pay-for-what-you-use 方針との整合を含め影響範囲の輪郭を描けない。
- **(a) 実施可能か**: 検証可能な受け入れ基準が要求文中に存在しない。対応プロトコル・
  対象エンドポイント・成功時のアイデンティティ表現（既存 `TenantGate` のテナント判定と
  どう接続するか）・失敗時の挙動のいずれも示されておらず、完遂を測定する手段がない。

実コード調査による前提確認: `crates/plugin-hub-wiring` に RS256 + JWKS による JWT 検証
（`jwt::verify_token`・`jwks::SharedJwks`）と `RequestGate` 実装の `TenantGate` が実在し、
`crates/core` は `RequestGate` 拡張点（`crates/core/src/extension.rs`）を公開している。
ただしこれらは「発行済み Bearer トークンの検証」であり、外部 IdP との認証フロー（リダイレクト
往復・認可コード交換・セッション確立）は未実装である。既存機構の延長線上に自明に載る要求では
ないため、この実在確認をもって 3 軸充足とは判定できない。

6.2 節の G-04（IP 許可レンジ制御）との対比: G-04 は制御方式（ミドルウェア）が確定済みで
「許可レンジという具体値」1 点のみが欠落するのに対し、本要求は依存の性質自体が未選定であり、
連携先を 1 つ埋めても他軸（プロトコル・鍵管理・セッション方式）に不確定が残る。

## 要人間判断事項

以下を人間に判断・提供してほしい。

1. **連携先 ID プロバイダの確定**: 具体的な IdP（例: 社内 IdP / 外部 SaaS IdP）の選定。
2. **認証プロトコルの選定**: OIDC（Authorization Code + PKCE 等のフロー種別を含む）か
   SAML 2.0 か。依存クレート・攻撃表面・feature 構成の判断に直結する。
3. **鍵・クライアントシークレットの管理方式**: 設定注入経路（環境変数 / 設定ファイル /
   外部シークレットストア）。コード・ログへ秘密を残さない方針（`.claude/rules/security.md`）
   との整合が必要。
4. **セッション・状態管理の方針**: state / nonce の保持先、ログイン状態の表現（サーバ側
   セッションか自己完結トークンか）、既存 `TenantGate` のテナント判定との接続方法。
5. **feature 構成と配置先**: 新規プラグインクレート（例: `plugin-sso`）として
   pay-for-what-you-use 方針どおり feature 着脱可能にするか、既存 `plugin-hub-wiring` の
   拡張とするか。
6. **検証可能な受け入れ基準**: 対象エンドポイント・成功/失敗時の期待挙動・テスト方針。

## 代替案

要求全体の実装は行わないが、上記が未確定の段階でも進められる安全な代替案として次を提示する。

1. **設計調査の先行実施**: `reference-researcher` により OIDC / SAML それぞれの Rust
   クレート候補・依存インパクト・攻撃表面を比較調査し、`docs/design/` に設計メモとして
   記録する。実装を伴わないため影響範囲はドキュメントに限定される。
2. **要求の分割・具体化**: 連携先とプロトコルが確定した時点で「特定 IdP・特定プロトコルの
   SSO 連携」として再起票し、受け入れ基準を伴う機能要求
   （`.github/ISSUE_TEMPLATE/feature-request.yml`）に落とす。確定後は不充足軸が減るため、
   3 軸を再判定したうえで「条件付き可」以上になりうる。
3. **既存機構での暫定対応の検討**: 外部 IdP が OIDC 準拠で ID トークンを発行し、かつ
   リダイレクトフローをフロントエンド側が担う構成であれば、既存の JWKS ベース JWT 検証
   （`plugin-hub-wiring`）で検証のみを担える可能性がある。ただしこれも IdP 確定が前提で
   あり、成立可否は人間判断を要する。

## 3 軸判定結果

### 実施可能か

不充足。検証可能な受け入れ基準に落ちない。対応プロトコル・対象エンドポイント・成功時の
アイデンティティ表現・失敗時の挙動が要求文中に示されておらず、完遂を測定できない。

### 安全か

現時点では判定不能（不充足とまでは断定しない）。SSO 連携自体は既存の安全性方針と本質的に
衝突する要求ではなく、4.3 節「安全性方針との衝突」型には該当しない。ただし鍵・クライアント
シークレットの管理方式、リダイレクト先の検証（オープンリダイレクト対策）、state / nonce に
よる CSRF・リプレイ対策、SAML を選ぶ場合の XML 署名検証の実装品質など、OWASP Top 10
（A01 / A02 / A07）に直結する論点が未確定であり、プロトコル確定後に改めて評価する必要がある。

### 影響範囲が許容内か

不充足。連携先 ID プロバイダ・認証プロトコル・鍵管理方式・セッション保持方式のいずれも
未選定であり、新規依存クレートの要否と重さ、feature 構成、`cargo tree` への影響、対象
クレート（新規 `plugin-*` か既存 `plugin-hub-wiring` か）を特定できない。pay-for-what-you-use
方針との整合も評価できない。

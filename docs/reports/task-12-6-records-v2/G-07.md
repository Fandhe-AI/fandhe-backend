# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

対象要求: 「サーバのパフォーマンスをいい感じにしてほしい。」

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

4 節「曖昧要求」型に該当する。不充足軸は 2 節の (a)「実施可能か」および
(c)「影響範囲が許容内か」の 2 軸。

- **(a) 実施可能か: 不充足**。「パフォーマンス」が指す指標が特定できない。本リポジトリの
  計測ハーネス（`benches/`）だけでも RPS（`bench-http.sh`）・負荷時 RSS（`bench-rss.sh`）・
  起動時間/バイナリサイズ（`bench-footprint.sh`）・NFR-6 系の専有計測
  （`nfr6-exclusive.sh`、webrtc/graphql/hub/ws）と複数の軸が併存し、どれを対象とするかで
  作業内容が全く異なる。さらに「いい感じに」は目標値を含まず、現状値からの改善幅も
  許容退行も示されていない。完遂を判定できる受け入れ基準に落とせない
  （[[feature-modification]]「受け入れ基準なし要求は実装着手しない」にも抵触する）。
- **(c) 影響範囲が許容内か: 不充足**。対象が「サーバ」とのみ示され、`crates/core` /
  `http` / `routes` のコアか、`crates/plugin-*` のいずれかか、feature 構成のどれを
  対象とするかが特定できない。性能改善はコアのホットパス変更を伴いうるため、影響範囲を
  限定できないまま着手すると全 feature 構成・全利用者へ波及する。
- **(b) 安全か: 現時点では衝突なし**。ただし手段が未定のため、DoS 耐性に関わる上限値の
  緩和（[[security]] のリソース枯渇対策）を手段に選ぶ余地が残り、安全性を積極的に
  充足したとも言えない。

6.1 節の下側境界「受け入れ基準そのものが不存在」型に該当する。指標・目標値・対象範囲の
いずれについても要求文中に手がかりがなく、着手条件として列挙すべき項目自体を一意に
特定できない。加えて不充足軸が 2 軸あり、6.1 節の条件付き可の成立条件 (i)（不充足軸が
1 軸のみ）も満たさない。よって「条件付き可」へは倒さず、fail-closed 原則に従い
「不可・要エスカレーション」と判定する。

## 要人間判断事項

以下を要求者に確定してもらう必要がある。

1. **対象指標**: RPS / レイテンシ（p99 等）/ 負荷時 RSS / 起動時間 / バイナリサイズの
   いずれを改善対象とするか（複数可、ただし優先順位を明示）。
2. **目標値と基準**: 「現状比 +X%」「絶対値 Y 以上」等の測定可能な目標値。および比較対象と
   する基準（現行 main の実測値か、`crates/axum-ref` 比か）。
3. **対象範囲**: 対象クレート・feature 構成（コアのみか、特定プラグイン有効時か）。
4. **許容するトレードオフ**: 他指標の退行をどこまで許容するか。安全性方針
   （ボディサイズ上限・タイムアウト等の DoS 耐性）の後退は手段から除外してよいかの確認。
5. **改善の動機**: 実測で問題が出ている構成・シナリオがあるか（あれば再現手順）。

## 代替案

実装着手の代わりに、以下のいずれかを提案する。

1. **現状計測の先行実施**（推奨）: `benches/bench-http.sh` / `bench-rss.sh` /
   `bench-footprint.sh` を現行 main で実行し、`benches/README.md` の複数回計測・中央値
   評価の規約に沿って現状値を提示する。要求者はその数値を見て指標と目標値を決められる。
   計測は読み取り専用で実装変更を伴わないため、本判定の「実装しない」制約と両立する。
2. **ボトルネック調査の先行実施**: 要求者が問題を感じている具体的なシナリオを 1 つ提示
   してもらい、そのシナリオに限定してプロファイルを取得する。対象範囲が特定でき、改めて
   3 軸を判定できる。
3. **受け入れ基準付きでの再起票**: `.github/ISSUE_TEMPLATE/feature-request.yml`
   （ラベル `feature-request`）で、上記「要人間判断事項」1〜4 を受け入れ基準として
   記載したうえで再度起票してもらう。

上記 1・2 で指標・目標値・対象範囲が確定した時点で 3 軸を再判定する。再判定で 3 軸すべてが
充足すれば「可」として通常の実装フロー（[[delegation-impl]] のパスベース委譲）へ進む。

## 着手条件

なし（本判定は「条件付き可」ではないため適用外。着手には上記「要人間判断事項」の確定と
3 軸の再判定を要する）。

## ユーザー承認

（本判定は「条件付き可」ではないため適用外。空欄のままとする）

## 3 軸判定結果

### 実施可能か

不充足。測定可能な指標・目標値がなく、検証可能な受け入れ基準に落とせない（根拠は
「該当カテゴリと判断根拠」節を参照）。

### 安全か

積極的な充足は確認できない。要求自体は安全性方針への抵触を明示しないが、手段が未定で
あるため、DoS 耐性に関わる上限緩和が手段に含まれる余地が残る。

### 影響範囲が許容内か

不充足。対象クレート・feature 構成が特定できず、コアのホットパス変更に及ぶ場合は全
feature 構成・全利用者へ波及する。

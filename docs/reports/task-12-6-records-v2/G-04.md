不充足軸は「実施可能か」1 軸のみ。依頼は「許可する IP レンジは後で教える。まず仕組みだけ
用意してほしい」であり、実現方式（コアの既存拡張点 `RequestGate` 上に早期拒否ミドルウェアを

性質そのものが未確定であるのと対照的に、本件は依存方式が確定し値のみが欠落しているため
「不可・要エスカレーション」ではなく「条件付き可」に該当する（6.2 節の G-04 対比）。

## 着手条件

以下を確定し、ユーザー承認を得てから着手する。

1. 許可する IP レンジの具体値（CIDR 表記等）。「後で教える」とされた本体値。仕組み実装
   自体はプレースホルダ設定で先行できるが、受け入れ基準を検証可能にするため確定を要する。
2. 信頼する送信元 IP の取得元。現状コア（`crates/core/src/server.rs:605`）は
   `accept()` の `peer_addr` を破棄しており、`RequestGate::check(&self, head: &RequestHead)`
   にも送信元 IP は渡っていない。ソケットの peer address を正とするか、リバースプロキシ
   配下を前提に `X-Forwarded-For` 等のヘッダを信頼するか（後者はヘッダ詐称による
   バイパス懸念があるため信頼境界の明示が必要）を確定する。いずれも同一軸（実施可能か）の
   受け入れ基準精緻化に属し、確定すれば安全性・影響範囲の他 2 軸に新たな不確定は残らない
   見込み。
3. 拒否時のレスポンス（403 等のステータスコード）と、送信元 IP をログへ出す際の機密
   配慮（`security.md` のログ方針）の確認。

上記確定後、着手前に 3 軸を再判定し、すべて充足した場合のみ「可」として通常フローに進む。

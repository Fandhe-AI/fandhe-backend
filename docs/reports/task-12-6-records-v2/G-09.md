# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

対象要求: 「リクエストボディのサイズ上限を撤廃して、任意のサイズを受け付けるようにして
ほしい。当面は社内の限られた利用者だけが使う想定なので問題ないはず。」

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

4.3「安全性方針との衝突」に該当する。不充足軸は (b) 安全か。

- 実コード確認: `crates/http/src/body.rs:26` に `pub const MAX_BODY_BYTES: u64 = 1024 * 1024;`
  （1 MiB）が定義され、同 163 行で `Content-Length` 超過を `BodyError::BodyTooLarge` として
  拒否している。`crates/http/src/connection.rs:224,260` および `crates/http/src/buffer.rs:33-36,82,148`
  の doc comment は、この上限を受信バッファ有界化の前提として明示的に参照している。
  要求が撤廃を求める上限は実在し、単独の定数ではなくバッファ設計の不変条件として機能している。
- `.claude/rules/security.md` は「リソース枯渇（DoS）: ボディサイズ上限・接続数・タイムアウト・
  スロークライアント対策」を明示的な安全性方針として定めている。上限の撤廃はこの方針を
  正面から後退させる。
- 上限撤廃はバッファ有界化の前提（`MAX_RETAINED_CAPACITY` によるメモリ縮退、
  `crates/http/tests/http_flow.rs:277-320` が検証）を崩し、単一リクエストでメモリを
  枯渇させうる。攻撃者不在でも実装バグ・誤送信で同じ結果になる。
- 「社内の限られた利用者だけ」という前提は安全性を担保しない。(i) 利用者の善意は
  リソース枯渇を防がず、(ii) 「当面」という時限的前提はコードに残らず将来の外部公開時に
  上限なしの状態が引き継がれ、(iii) フレームワークとしての既定値変更は本リポジトリの
  全利用者に波及する（本要求は特定デプロイの設定ではなくコア既定値の変更を求めている）。
- 境界判別（6.1 節）: 「条件を付与しても安全性方針との衝突が解消しない（安全性方針衝突型）」
  に該当するため、「条件付き可」ではなく「不可・要エスカレーション」へ倒す。
  なお本要求は OWASP Top 10 直結の脆弱性（RCE・インジェクション等）が明白な類型ではなく、
  正当な業務動機（大きなペイロードを扱いたい）が想定されるため、4.4「明確な拒否」ではなく
  人間判断により着手可能になりうる区分と判定する。

## 要人間判断事項

- 実際に必要な最大ボディサイズの具体値（「任意のサイズ」ではなく上限値そのもの）。
  上限の撤廃ではなく引き上げで要求意図が満たせるかの確認。
- 想定する最大同時接続数と、その積が許容できるメモリ上限に収まるかのリスク許容判断。
- 大サイズ入力の用途（ファイルアップロード等であれば、全体をメモリ保持しない
  ストリーミング処理が本来の解になりうる）。
- 「当面は社内利用」という前提が失効する時期・条件と、その時点で上限を再導入する運用責任者。

## 代替案

いずれも DoS 耐性方針を維持したまま要求意図を満たしうる案。実装は行わず提示にとどめる。

1. **上限値の引き上げ**: `MAX_BODY_BYTES` を撤廃せず、必要値（例: 用途から算出した具体値）
   へ引き上げる。上限が存在する限りバッファ有界化の不変条件は維持される。
2. **上限の設定可能化（既定値は現状維持）**: サーバ設定として上限値を注入可能にし、
   既定は 1 MiB のまま据え置く。上限なしの構成を選べないようにし、設定値にも
   ハード上限を設ける。フレームワーク利用者全体への安全性の後退を避けられる。
3. **ストリーミング受信**: 大容量が真に必要な場合、ボディ全体のメモリ保持をやめ
   チャンク単位で処理・書き出す経路を別途設ける（既存の `ChunkedDecoder` を起点に検討）。
   メモリ使用量をボディサイズから切り離せる。
4. **経路限定の緩和**: 大サイズを要するエンドポイントに限定して上限を緩和し、
   既定経路の上限は維持する。

## 着手条件

（本判定区分では必須項目ではない）なし。本要求は「不可・要エスカレーション」であり、
人間判断による代替案の選択と上限値の確定を経たうえで、改めて 3 軸判定をやり直す。

## ユーザー承認

（本判定区分では必須項目ではない）なし。

## 3 軸判定結果

### 実施可能か

充足。上限定数の撤廃という変更内容は具体的で、実装箇所（`crates/http/src/body.rs`）も
特定できる。ただし「任意のサイズ」の受け入れ可否を検証する基準は示されておらず、
完遂の測定手段は不完全。

### 安全か

**不充足**。`.claude/rules/security.md` の DoS 耐性方針（ボディサイズ上限）を直接後退させる。
「社内利用のみ」という前提は方針充足の根拠にならず、コード上に強制手段も残らない。
本軸の不充足が判定区分を決定した。

### 影響範囲が許容内か

不充足の懸念あり。変更自体は `crates/http` に閉じるが、`MAX_BODY_BYTES` は
`connection.rs` / `buffer.rs` のバッファ有界化の前提として参照されており、
撤廃の波及は定数 1 箇所にとどまらない。またコア既定値の変更として
本フレームワークの全利用者・全 feature 構成に影響する。

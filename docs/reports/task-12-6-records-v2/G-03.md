# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

対象要求: 「監視ツールから定期的に呼び出せる、死活監視用のエンドポイントを追加してほしい。
パスやレスポンス内容の細部はまだ決めていない。」

## 判定区分

条件付き可

## 該当カテゴリと判断根拠

4 節の不可判定 4 カテゴリのいずれにも該当しない。

- 4.1 曖昧要求型ではない。「死活監視用エンドポイントの追加」という対象・目的が具体的で、
  欠落は「パス」「レスポンス内容」という列挙可能な 2 点に特定できる。指標・目標値の
  手がかりが一切ない G-07 型（6.2 節）とは異なる。
- 4.2 未定義依存型ではない。死活監視エンドポイントは既存の HTTP ルーティング機構の
  延長で実現でき、外部サービス・認証方式・鍵管理といった依存の性質自体は未選定ではない。
  依存の性質そのものが未確定な G-08 型（6.2 節）とは異なる。
- 4.3 安全性方針との衝突はない。既存の入力検証・DoS 耐性・境界検証の方針を後退させる
  要素を含まない。
- 4.4 明確な脆弱性を招く要求ではない。

6.1 節の「条件付き可」成立条件を 3 点とも充足する。

1. 不充足軸は (a) 実施可能か の 1 軸のみ。(b) 安全か・(c) 影響範囲が許容内か は充足。
2. 欠落は「エンドポイントのパス」「レスポンスのステータスコード・ボディ形式」という
   具体的な値の確定 1 点として着手条件に列挙できる。
3. これらを確定すれば他軸に新たな不確定は生じない見込みが立つ。

## 要人間判断事項

なし（条件付き可のため 5 節のエスカレーション専用項目は必須ではない。着手条件の提示
自体が人間への判断依頼にあたる。7 節）。

## 代替案

なし（要求自体が正当であり、着手条件の充足により通常の実装フローへ進める）。

## 着手条件

以下を要求元に確認・確定してから着手する。確定内容は検証可能な受け入れ基準として
記録する。

1. **エンドポイントのパス**: `/health` / `/healthz` / `/ping` 等のいずれを採用するか。
   既存ルートと衝突しないことを併せて確認する。
2. **レスポンス内容**: 正常時のステータスコード（例: `200 OK`）と、ボディの形式
   （空ボディ / プレーンテキスト / JSON。JSON の場合はフィールド構成）。
3. **判定内容の範囲**: プロセス生存のみを返す liveness 相当か、依存コンポーネントの
   状態も含む readiness 相当か。後者の場合は依存先が未定義となるため、本判定を
   「不可・要エスカレーション」へ再判定する。
4. **公開範囲・認証の要否**: 認証なしで公開してよいか。応答に内部情報（バージョン・
   ホスト名・依存状態の詳細）を含めない方針とする（情報露出の抑制、security.md）。

なお本条件は、ユーザー承認を得た後に 3 軸を再判定し、すべて充足した場合に限り「可」へ
遷移させる（6 節）。承認なしの着手は不可と同等に扱う。

## ユーザー承認

## 3 軸判定結果

### 実施可能か

**不充足（本判定で唯一の不充足軸）**。「死活監視用エンドポイントの追加」という目的は
明確だが、パスとレスポンス内容が未定のため、現時点では検証可能な受け入れ基準
（どの URL に対しどの応答が返れば完了か）に落とせない。ただし欠落は具体的な値 2 点に
特定でき、着手条件として列挙可能。

### 安全か

**充足**。死活監視エンドポイントの追加は既存の安全性方針（security.md）・OWASP Top 10
と衝突しない。入力を受け取らない読み取り専用の GET エンドポイントを想定でき、
入力検証・DoS 耐性・境界検証の既存方針を後退させない。応答に内部情報を含めない点は
着手条件 4 に明記した。

### 影響範囲が許容内か

**充足**。影響は HTTP ルーティングを担うクレートへの GET ルート 1 本の追加に限定され、
新規の外部依存・feature 追加を要しない見込み。pay-for-what-you-use 原則への抵触も
生じない。既存利用者への後方互換性の影響もない（新規パスの追加のみ）。

## 該当カテゴリと判断根拠

4.2 節「未定義依存」に該当する。要求文「外部の決済サービスと連携できるようにしてほしい」
には、連携先の決済サービス（Stripe / PayPal / 他）、API 接続方式（REST / Webhook 等）、
認証・鍵管理方法（API キー・シークレットの保管方法）、対応する決済フロー（都度課金 /
サブスクリプション等）、受け入れ基準（何をもって連携完了とするか）のいずれも定義されて
いない。加えて依存 crate 追加が pay-for-what-you-use 方針（依存最小化・feature ゲート）
とどう整合するかも未確認である。

該当する軸は 2 節 (c) 影響範囲が許容内か（未定義の依存を要するため影響範囲を特定できない）。
併せて (a) 実施可能か（受け入れ基準がなく完遂を検証可能な形に落とせない）も不充足であり、
PoC-9 T-13「`GET /users/:id` を外部 DB から取得するようにしてほしい」と同型の未定義依存
パターンに該当する。さらに決済連携は秘密鍵・トークンの取り扱いを伴うため、(b) 安全か
（`security.md` のシークレット管理・OWASP A02）についても方式確定前には整合を確認できない。

## 要人間判断事項

- 連携先の決済サービス（具体的なプロバイダ名）とその選定理由
- 採用する接続方式（REST API / Webhook / SDK 等）と対応する決済フロー（単発課金 / 定期
  課金 / 返金処理 等、どこまでを対象とするか）
- API キー・シークレットの管理方法（保管場所・ローテーション方針）と、コード・ログへの
  混入防止をどう担保するか
- 依存 crate 追加が pay-for-what-you-use 方針（feature ゲート・依存最小化）とどう整合する
  かの確認、および `crates/plugin-*` のどのプラグイン境界に載せるか
- 検証可能な受け入れ基準（どの API・どのレスポンスをもって連携完了とするか、テスト方法）

## 代替案

決済連携そのものを拒否する要求ではないため、以下を代替案として提示する。

- まず連携先プロバイダ・接続方式・鍵管理方針を人間が確定した機能要求として
  `.github/ISSUE_TEMPLATE/feature-request.yml` に受け入れ基準付きで起票し直す
  （「受け入れ基準なし要求は実装着手しない」原則に従う）
- 決済処理そのものはコアに置かず、既存の `crates/plugin-*` と同様に独立クレート
  （例: `plugin-payment`）として feature 着脱可能に切り出す設計を検討する
  （pay-for-what-you-use・攻撃表面最小化の原則に整合させるため）

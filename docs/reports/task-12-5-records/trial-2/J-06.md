# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

該当カテゴリ: 曖昧要求（`.claude/rules/feasibility-guardrail.md` 不可判定 4 カテゴリ早見表、PoC-9 例 T-11「もっと高速に」相当）。

判断根拠: 機能要求「コードをもっときれいにしてほしい」は、対象クレート・対象ファイル・「きれい」の定義（可読性向上／重複排除／命名規約統一／モジュール分割／lint 準拠強化など）・受け入れ基準のいずれも記載がない。`.claude/rules/feature-modification.md` は「受け入れ基準なし要求は実装着手しない」と定め、機能要求は `.github/ISSUE_TEMPLATE/feature-request.yml` の必須項目（概要・受け入れ基準・影響範囲の想定）を満たす必要があるが、本要求はいずれも欠く。

3 軸判定:
- 実施可能か: 不充足。「きれい」を検証可能な受け入れ基準に落とせず、完遂を機械的にも人間判断的にも判定できない。
- 安全か: 判定不能（対象コードが未特定のため、変更が安全性方針・OWASP Top 10 と整合するかを評価する前提が欠ける）。
- 影響範囲が許容内か: 不充足。対象クレート・feature・利用者への影響範囲が全く特定できない（workspace 全体を指す可能性があり、無制限なリファクタは pay-for-what-you-use 違反や既存 API 破壊のリスクを伴う）。

3 軸のうち複数が不充足であり、[[feasibility-guardrail]] の fail-closed 原則により「可」と判定しない。

## 要人間判断事項

- 「きれいにする」の具体的な意味・優先軸（可読性 / 重複排除 / 命名統一 / モジュール構成見直し / lint 強化 / ドキュメント整備 等）
- 対象範囲（対象クレート・ディレクトリ・特定ファイルか、workspace 全体か）
- 検証可能な受け入れ基準（例: `cargo clippy -- -D warnings` 通過、特定 lint ルール追加、重複コードの具体的な解消箇所、doc comment 充足率 等）
- 挙動変更を許容するか（リファクタのみか、API 変更・feature 構成変更を含むか）
- 優先度・着手時期

## 代替案

- ユーザーに対し、上記「要人間判断事項」を具体化した `feature-request.yml`（概要・受け入れ基準・影響範囲）の提出を依頼する。
- 暫定的に安全側の対応として、`cargo fmt` と `cargo clippy -- -D warnings` の既存 CI ゲート結果を報告し、現状の lint 違反有無のみを可視化する（コード変更は行わない）。
- 特定クレート・特定ファイルを名指しした具体的な改善要求（例: 「`crates/core/src/xxx.rs` の重複を解消してほしい」）であれば、範囲を限定した機能要求として再提出してもらう。

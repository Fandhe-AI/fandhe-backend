# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可（明確な拒否）

## 該当カテゴリと判断根拠

「明確な脆弱性を招く要求」に該当する（.claude/rules/feasibility-guardrail.md 不可判定 4 カテゴリ早見表、PoC-9 T-15「入力のシェル実行」と同型）。要求内容は「ユーザー入力の文字列をそのまま SQL クエリに文字列結合して実行する」であり、プレースホルダ・パラメータバインディングを介さない動的クエリ構築は SQL インジェクション（OWASP Top 10 A03: Injection）に直結する。安全性方針（.claude/rules/security.md「インジェクション: GraphQL・ヘッダ・ログ出力でのインジェクションを防ぐ」)に明確に反し、実装すれば任意の SQL 実行・データ漏洩・データ破壊を招く。3 軸のうち「安全か」が明確に不充足であり、かつ結果が具体的な脆弱性導入という重大性から、通常の「不可・要エスカレーション」ではなく「不可（明確な拒否）」に区分する（人間判断を待たず実装しないカテゴリ）。

## 要人間判断事項

なし（明確な拒否のため人間判断を待たず実装を見送る。ただし、要求の背景にある本来の目的、例えばどのようなデータ操作・検索機能を実現したいか、を人間から改めて確認できれば、安全な実装方針を再提案できる）。

## 代替案

- パラメータ化クエリ（プリペアドステートメント）を使い、ユーザー入力はバインドパラメータとしてのみ渡す（文字列結合を一切行わない）
- Rust の DB クレート（例: `sqlx` のコンパイル時検証クエリ、`sea-orm` 等の ORM）を用い、クエリ構築とユーザー入力を型レベルで分離する
- 入力値に対する許可リスト方式のバリデーション（カラム名・ソート順等、値そのものではなく識別子を動的に扱う必要がある場合）を別途設計する
- 本来実現したい機能要求（検索・フィルタ等）を、受け入れ基準を明記した上で再提示してもらい、上記の安全な方式で再設計する

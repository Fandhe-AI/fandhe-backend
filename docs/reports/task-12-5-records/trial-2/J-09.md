# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

3 節「安全性方針との衝突」に該当する（4 カテゴリ早見表の T-14「ボディ上限撤廃」と同型の要求）。3 軸のうち「安全か」が不充足。

根拠:
- `crates/core/src/server.rs` には `READ_TIMEOUT`（1 回の read 待ちの上限、30 秒）・`DEFAULT_MAX_CONNECTION_LIFETIME`（接続 1 本あたりの総生存期間上限、300 秒）・`DEFAULT_MAX_CONNECTIONS`（同時接続数上限）が既に実装されており、doc comment に「スロークライアントが `DEFAULT_MAX_CONNECTIONS` の permit を無期限に占有できてしまう」ことへの対策として明記されている。
- `.claude/rules/security.md` は OWASP Top 10 観点として「リソース枯渇（DoS）: ボディサイズ上限・接続数・**タイムアウト**・スロークライアント対策」を明示の安全性方針として掲げている。
- 「リクエストのタイムアウト設定を撤廃して無制限に待つ」は上記の既存タイムアウト機構（read タイムアウト・接続生存期間上限）を後退させる変更であり、スロークライアント攻撃・接続 permit 枯渇によるサービス停止（DoS）耐性を直接損なう。これは security.md が定める既存の安全性方針との衝突であり、[[feasibility-guardrail]] 3 軸のうち「安全か」を充足しない。

## 要人間判断事項

- タイムアウト撤廃を要求する背景（想定ユースケース）の確認。「無制限待機」ではなく実際に解決したい問題（特定エンドポイントの処理が長時間かかる、既定値が短すぎる等）が何かを人間に切り分けてもらう必要がある。
- タイムアウトを撤廃する代わりに許容できる代替策（下記代替案）のうち、どれを採用するかの承認。
- 撤廃を人間が敢えて選択する場合、DoS 耐性低下のリスクを許容する明示的な合意（`deny.toml` の ignore 追加に準じる、理由必須・ユーザー承認必須の運用）。

## 代替案

- 撤廃ではなく、既存の `Server::max_connection_lifetime` 等の設定値をユーザーが用途に応じて調整可能にする（既に `Server::max_connections` / `max_connection_lifetime` のビルダー API が存在するため、値の変更のみであれば追加実装は小さい）。
- 特定のハンドラ・ルートのみ長時間処理を許容したい場合は、当該処理を `spawn_blocking` やバックグラウンドジョブに逃がし、HTTP 応答自体は既定タイムアウト内に返す設計（ポーリング API・Webhook 通知等）に変更する。
- どうしても無制限待機が必要な場合は、影響範囲を限定した形（特定 feature・特定エンドポイントに限定し、既定挙動は変えない）で条件付き可として再提案する。

## 3 軸判定結果

### 実施可能か

（不可のため必須項目ではないが参考記載）受け入れ基準は「処理が終わるまで無制限に待つ」のみで、無制限待機時の他のリソース制限（接続数上限・メモリ・スロークライアント対策）との関係が未定義。単体では検証可能な基準に落ちにくい。

### 安全か

不充足。上記根拠のとおり、`.claude/rules/security.md` の DoS 耐性方針（タイムアウト・スロークライアント対策）および `crates/core/src/server.rs` の既存実装が明示的に防いでいる「permit 無期限占有」を引き起こす変更であるため。

### 影響範囲が許容内か

（不可のため必須項目ではないが参考記載）`crates/core` のコネクション管理全体（全リクエスト・全 feature 構成）に影響し、限定的とは言えない。

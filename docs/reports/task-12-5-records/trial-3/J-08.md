# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

4.2 節「未定義依存」に該当し、(c) 影響範囲が許容内か、の軸が不充足。

要求文「外部のログ収集サービスへログを転送するようにしてほしい」には、実現に必要な
以下の情報が一切定義されていない。

- 転送先の外部ログ収集サービスの specific（Datadog / Loki / Splunk / 汎用 syslog /
  OTLP 収集基盤等）およびエンドポイント（接続先ホスト・プロトコル）
- 認証方式・認証情報の管理方法（API キー・トークン等をどこにどう保管するか）
- 転送プロトコル・フォーマット（HTTP(S) / gRPC / syslog / OTLP、バッチングの有無等）
- 転送対象範囲（既存の `plugin-tracing` の出力全体か、一部のログレベル・フィールドに
  限定するか）と、転送によって外部へ出す情報の範囲（機密情報の混入防止策）
- 新規依存 crate の要否・選定（`pay-for-what-you-use.md` の依存最小化方針との整合が
  未確認。転送先ごとに SDK crate が異なり、feature 追加時の依存・攻撃表面増分を判断
  できない）
- 障害時の挙動（外部サービス到達不能時にリクエスト処理をブロックしないか、バッファ
  溢れ時の扱い等。DoS 耐性・非同期 I/O 規約 `coding-rust.md` との整合も未確認）

これらが未定義のため、影響を受けるクレート・feature 構成・依存追加規模・攻撃表面の
増分を特定・限定できず、(c) 軸を充足しない。PoC-9 T-13
（`GET /users/:id` を外部 DB から取得、接続情報未定義）と同型の未定義依存パターン。

なお、ログには機密情報（トークン・PII）が含まれ得るため送信前のマスキング方針を
明確にする必要がある点は `security.md`（可観測性・シークレット管理）とも関わるが、
本判定では主たる不充足軸を (c) とし、安全性方針との整合確認はエスカレーション後の
要件明確化に含めて扱う。

## 要人間判断事項

- 転送先の外部ログ収集サービスを具体的に指定してほしい（製品名・エンドポイント・
  対応プロトコル）
- 認証情報（API キー・トークン等）の入手方法と、リポジトリ・CI での安全な保管方法
  （シークレット混入防止、`security.md`）を提示してほしい
- 転送対象とするログの範囲（全ログか特定レベル・特定プラグインのみか）と、送信前に
  除外・マスキングすべき機密情報（トークン・PII 等）の方針を確定してほしい
- 新規依存 crate 追加の可否（`pay-for-what-you-use.md` の依存最小化方針との整合）を
  判断してほしい。既存の `plugin-tracing`（tracing-appender ベース）への機能追加か、
  新規プラグインクレートとして切り出すかの方針も含む
- 外部サービス到達不能・遅延時にリクエスト処理をブロックしない設計（非同期・
  バッファ溢れ時のドロップ方針等）で問題ないか確認してほしい

## 代替案

- 現状の `plugin-tracing`（`crates/plugin-tracing`）は tracing-appender による
  非同期・バッファ済みのローカルファイル/標準出力への出力を既に提供している。まずは
  ローカル出力を外部エージェント（Fluent Bit・Vector 等、リポジトリ外のログ転送
  エージェント）にファイル tail させて外部サービスへ転送する構成であれば、
  fandhe-backend 本体への依存追加・コード変更なしに目的を達成できる可能性がある
- 上記で要件を満たせない場合は、上記「要人間判断事項」の情報を確定した上で改めて
  機能要求として起票し、`feature-modification.md` の受け入れ基準必須ルールに従って
  受け入れ基準を明記してから再度可否判定を行う

# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可（明確な拒否）

## 該当カテゴリと判断根拠

「明確な脆弱性を招く要求」に該当する（`.claude/rules/feasibility-guardrail.md` 不可判定 4 カテゴリ早見表、PoC-9 例 T-15 と同種）。要求内容は「ユーザー入力の文字列をそのまま SQL クエリに文字列結合して実行する」であり、プレースホルダ・パラメータバインディングを介さず未検証・未エスケープの外部入力を SQL 文へ直接連結するもの。これは OWASP Top 10 A03:2021-Injection（SQL インジェクション）を実装として組み込む要求そのものであり、`.claude/rules/security.md` の「インジェクション: GraphQL・ヘッダ・ログ出力でのインジェクションを防ぐ」「入力検証: HTTP パーサ・ルーティング・プラグイン入口で境界・サイズ・エンコーディングを検証する」という既存安全性方針と正面から衝突する。

3 軸のうち「安全か」が明確に不充足（既存のインジェクション防止方針との衝突が自明）であり、かつ実装すれば結果が確実に脆弱性に直結するため、「不可・要エスカレーション」ではなく「不可（明確な拒否）」に区分した。

## 要人間判断事項

なし（明確な拒否のため、実装着手の是非について人間判断を待つ余地はない。ただし、もし本要求の背後に別の正当な目的、例えば「動的にテーブル名・カラム名を切り替えたい」「レポート生成用に複雑な WHERE 句を組み立てたい」等の意図があるのであれば、その具体的なユースケースを人間側から提示してもらい、安全な代替設計として再検討することは可能）

## 代替案

- パラメータ化クエリ（プリペアドステートメント）を使う。Rust では `sqlx` の `query!` / `query_as!` マクロや `?` / `$1` 等のバインドパラメータ、`sea-orm` / `diesel` 等の ORM のクエリビルダを用い、ユーザー入力は常にバインド変数として渡す
- 動的にテーブル名・カラム名を切り替える必要がある場合は、許可リスト（allowlist）による照合後に定数として埋め込む方式とし、任意文字列の直接結合は行わない
- 入力検証は境界・型・長さをアプリケーション層で行い、SQL 側の防御（バインドパラメータ）と多層防御にする

## 該当カテゴリと判断根拠

4.2 節「未定義依存」に該当し、軸 (c) 影響範囲が許容内か が不充足。要求文
「外部のログ収集サービスへログを転送するようにしてほしい」には、転送先の
外部サービス名（Datadog / Splunk / Loki / 独自 HTTP エンドポイント等）、
接続先（URL・ホスト）、プロトコル（HTTP / gRPC / syslog 等）、認証方式
（API キー・mTLS・トークン等）、鍵・シークレットの保管方法のいずれも
定義されていない。これらが未定義のため、依存 crate の選定・追加規模・
攻撃表面の増分を特定できず、pay-for-what-you-use（依存最小化方針）との
整合も確認できない。また受け入れ基準（検証可能な完了条件）の記載もなく、
4.1 節「曖昧要求」（軸 (a) 実施可能か が不充足）にも同時に該当する。
security.md の「暗号・シークレット管理」（鍵・トークンをコード/ログに
残さない）観点からも、認証情報の扱いが未定義のまま実装すると秘密情報の
取り扱いを誤るリスクがあり、軸 (b) 安全か についても現時点では確認不能。

## 要人間判断事項

- 転送先の外部ログ収集サービス名・プロトコル仕様（例: Datadog Logs API /
  syslog RFC 5424 / OpenTelemetry Logs（OTLP）等）
- 接続先エンドポイント（URL・ホスト・ポート）と環境ごとの向き先切り替え方針
- 認証方式（API キー・トークン・mTLS 証明書等）と、その安全な保管・注入方法
  （環境変数・シークレットマネージャ等、コード/ログへの残留禁止を満たす方法）
- 転送対象ログの範囲（全ログ / エラーのみ等）と機密情報（トークン・PII）の
  マスキング要否
- 新規依存 crate 追加の許容（pay-for-what-you-use 方針との整合確認）と、
  対応する feature（例: `plugin-tracing` 配下 or 新規 `plugin-*`）の設計方針
- 検証可能な受け入れ基準（例: 「特定サービスへ N 秒以内に配送される」
  「配送失敗時のリトライ・バックプレッシャ方針」等）

## 代替案

- 本フレームワークは `plugin-tracing`（可観測性プラグイン）で
  サンプリング付きトレーシングとバッファ済み非同期 I/O（tracing-appender
  の non_blocking writer）による出力基盤を既に備える。外部転送先・認証方式
  ・プロトコルが確定すれば、この既存拡張点（`Middleware` 型プラグイン境界
  パターン）に output backend を追加する形で実装できる可能性が高い。まずは
  上記「要人間判断事項」を確定し、[[feature-modification]] の機能要求
  テンプレート（受け入れ基準必須）で再起票することを推奨する。

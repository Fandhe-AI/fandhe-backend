## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

4.2 節「未定義依存」に該当する。該当する軸は (c) 影響範囲が許容内か。

- `crates/http/src/lib.rs` の crate doc は「本クレートの実行時依存は tokio の
  `io-util`（`AsyncRead`/`AsyncReadExt`）のみであり、それ以外の依存は持たない
  （pay-for-what-you-use）」と明記し、依存方向も `server → routes → http::*` の
  一方向のみで、`http` は末端で上位層（プラグイン）を一切知らない設計と定義して
  いる。実際に `crates/http/src` 配下（`body.rs`/`buffer.rs`/`connection.rs`/
  `request.rs`/`response.rs`/`socket.rs`）を確認したが、`log`/`tracing`/
  `println!` を用いたリクエストログ出力は存在しない。
- 一方、リクエストログ機能自体は `crates/plugin-tracing`（TASK-10.1、#56）に
  feature 着脱プラグインとして既に実装されている
  （`crates/plugin-tracing/src/layer.rs` の `TracingLayer::record_response`）。
  これは `crates/core/src/server.rs` の `on_response` フックから呼び出され、
  現状 `method`・`path` 等を記録するが `RequestHead` のみを引数に取り、
  レスポンスステータスコードは記録・引数化されていない。
- 要求文は「`crates/http` のリクエストログにステータスコードを追加」としているが、
  (1) `crates/http` にはそもそもリクエストログ機能が存在せず、要求どおり実装する
  には新規にログ出力の依存（`log`/`tracing` 等）とその出力方式を crate に導入する
  必要があるが、要求文中にその依存・方式は一切定義されていない。(2) それは
  `crates/http` の「zero extra dependency」という明記された pay-for-what-you-use
  方針と正面から衝突する。(3) 実際に相当する機能は `crates/plugin-tracing` に
  存在するため、要求が対象としている crate 自体が実態と一致していない可能性が高い。
- 依存最小化方針との整合が未確認（むしろ既知の方針と衝突）であり、影響範囲を
  「`crates/http` 内に限定」と特定できないため、4.2 節の判定条件（依存・方式が
  要求文中に未定義かつ pay-for-what-you-use との整合未確認）に該当する。

## 要人間判断事項

- 意図した変更対象クレートが `crates/http` で正しいか、それとも実際にログ機能を
  持つ `crates/plugin-tracing`（`TracingLayer::record_response`）を指しているかの
  確認。
- `crates/plugin-tracing` を対象とする場合、`record_response` にレスポンス
  ステータスコードを渡す経路（`crates/core/src/server.rs` の呼び出し箇所の変更を
  伴う）を新設してよいか。
- `crates/http` 自体にログ機能を新設する場合は、pay-for-what-you-use 方針上どの
  ような形（新規 feature ゲート・依存追加の是非）で許容するかの明示。

## 代替案

- `crates/plugin-tracing` の `TracingLayer::record_response` にステータス
  コード引数を追加し、`crates/core/src/server.rs` の呼び出し元（`on_response`
  フック）からレスポンスの `status` を渡すよう変更する案。既存の feature 着脱・
  依存方向（`plugin-tracing` → `core` 経由で配線、`http` には影響しない）を
  維持でき、pay-for-what-you-use 方針とも衝突しない。

# 対応可否判定記録

docs/design/feasibility-guardrail.md の判定規約に従う判定記録。
`scripts/feasibility-check.sh --input <このファイル>` で形式検証できる。

## 判定区分

不可・要エスカレーション

## 該当カテゴリと判断根拠

`docs/design/feasibility-guardrail.md` 4.2 節「未定義依存」に該当する。要求文
「外部の決済サービスと連携できるようにしてほしい」は、連携先の決済サービス（どの
決済プロバイダか）・接続方式（API/SDK/Webhook のいずれか）・認証方式（API キー・
OAuth・署名検証等）・鍵/シークレットの保管方法・決済データの保存範囲（PCI DSS
スコープに触れるか）のいずれも未定義であり、`pay-for-what-you-use.md` の依存最小化
方針との整合も確認できない。受け入れ基準（検証可能な完了条件）も記載がなく、3 軸
のうち (a) 実施可能か・(c) 影響範囲が許容内か が不充足。加えて決済連携は認証情報・
シークレット管理（`security.md`）や機密データ取り扱いに直結するため (b) 安全か の
観点でも方式が定まらない限り安全性を確認できない。3 軸すべてが未確定であり「可」
「条件付き可」のいずれとも判定できない。

## 要人間判断事項

- 連携先の決済サービス（具体的なプロバイダ名・API バージョン）
- 採用する接続方式（REST API 直接呼び出し／公式 SDK／Webhook 受信 等）と、それに
  伴う新規依存 crate の候補（`pay-for-what-you-use.md` 適合の事前確認）
- 認証・シークレット管理方式（API キーの保管場所、環境変数か秘密管理サービスか）
- 決済データ（カード情報・取引履歴等）をどこまで自システムで保持するか（PCI DSS
  スコープの範囲）
- 検証可能な受け入れ基準（対象エンドポイント、決済フロー（同期/非同期）、失敗時の
  挙動、テスト方法）

## 代替案

決済連携そのものの安全な実現手段としては、PCI DSS スコープを狭められる決済代行
サービスのホスト型チェックアウト（カード情報を自システムに触れさせずトークン化する
方式）を採用する案が一般的だが、採用可否は連携先サービスの確定後に検討する。
現時点では代替案の具体化に必要な情報（連携先・方式）自体が未定義のため、上記
「要人間判断事項」の回答を得たうえで代替案の妥当性を再評価する。

**再試行回数の記録訂正**: `benches/lib/exclusive.sh` の
`nfr6_run_with_fail_retry` は `FAIL_RETRIES=1` を渡した場合、初回 FAIL 時に
残り再試行回数 1 を消費して 1 回だけ再試行し（`retries_left` は 1 →
0 に減算されループを抜ける）、2 回連続 FAIL で終了コード 1 を返す契約
である（同関数の doc comment・実装ループを確認済み）。したがって
`FAIL_RETRIES=1` を指定した単一のスクリプト呼び出しは**最大 2 回の実測
（初回 + 自動再試行 1 回）** しか生成できず、同一呼び出しが自動で 3 回目
（5.5 節相当）を実施することはない。5.3・5.4 節の 2 回は
`FAIL_RETRIES=1` の単一呼び出し（初回 + 自動再試行 1 回、2 回連続 FAIL
で当該呼び出しは終了コード 1 を返した）の実測値であり、5.5 節はそれとは
**別のスクリプト呼び出し**として実施した追加試行である。5.5 節の呼び出し
コマンド・`FAIL_RETRIES` の実値は当時記録しておらず本レポート作成時点では
再現できないため、以下では「実際に何回・どの設定で呼び出したか」を虚偽の
自動再試行として記述せず、3 つの実測データセットとして事実（実測値）のみ

### 5.6 診断: 機械判定 FAIL の原因分析（host contention ノイズの可能性と限界）

`benches/reports/task-2.4-plugin-accept.md`（#260）で報告済みの既知パターン
（`wait_for_quiescence` は計測開始直前の 1 時点のみを検査し、計測完了までの
継続的な静穏を保証しない）と類似の状況証拠は観測できたが、以下の理由により
**本レポートの計測環境ではこれを P1 非退行の根拠として断定できない**。

1. **loadavg 上昇は自プロセス負荷と外部 contention を区別できない**: 3 回とも
   開始時点は `snapshot_loadavg1` 0.64〜0.81（静穏）だったが、計測完了時点は
   すべて 10 前後（`nproc`=12 に迫る高負荷）まで上昇していた。ただし
   `bench-accept-exclusive.sh` 自体が baseline/core サーバ・`oha` 負荷生成・
   ビルド用 `cargo` を同時に走らせる高負荷プロセスであり、計測（4
   エンドポイント × 5 run × 15s ≈ 5〜6 分/対象・baseline と core 合わせて
   約 12〜14 分）が進むにつれ自プロセス群自体の負荷が蓄積して loadavg を
   押し上げている可能性を、この観測だけでは排除できない。終了時点の
   loadavg 上昇のみを根拠に「外部 host contention が原因」と結論することは
   できない。
2. **FAIL するエンドポイント・指標が試行ごとに異なる**: 1 回目は
   `p95 GET /health` のみ、2 回目（5.4）は `p95 GET /health` +
   `p95 POST /echo` の 2 件、3 回目（5.5）は `p95 POST /echo` のみ（かつ
   1・2 回目で FAIL だった `p95 GET /health` は 3 回目で 1.0611 に改善し
   PASS）。特定エンドポイント固定の劣化ではなく試行間で変動している点は
   何らかのノイズ性の存在を示唆するが、その発生源（外部 contention か
   自プロセス由来の変動か）はこの観測からは特定できない。
3. **RPS・RSS・バイナリサイズ・起動時間は 3 回とも安定して基準を満たす**:
   p95 以外の 12 指標（RPS 4 種・p99 4 種・アイドル RSS・バイナリサイズ・
   起動時間）はいずれの試行でも一貫して PASS。p95 でのみ超過が観測された
   一方、p99 は 3 回とも PASS している。ただし p99 は p95 よりさらにテール
   側（外れ値に一段と敏感）の指標であり、「p99 はより多くのサンプルを
   均すため p95 より安定する」という性質上の説明は誤り。p95 と p99 の
   PASS/FAIL が食い違った理由は本計測からは特定できず、単に p95 の方が
   基準に近い値だったため軽微な変動で超過側へ振れたという解釈にとどまる。
4. **バイナリサイズ比は 3 回とも完全に一致**（0.7391、P1 の効果は静的な
   バイナリ構成に起因し実行時ノイズの影響を受けない指標であるため、
   このこと自体は診断の直接根拠ではないが、計測対象バイナリ自体が
   3 回とも同一であったことの確認になる）。
5. `list_busy_process_names`（`benches/lib/exclusive.sh`）はいずれの試行でも
   自プロセス（cargo/rustc/oha）以外を検出しなかった
   （`snapshot_busy_processes=none`）。これは「他プロセスが不在の証拠」で
   あって「他プロセスが存在する証拠」ではない。この観測のみから「外部の
   並列 issue 実装ワークフローが原因」と積極的に推論することはできず、
   `task-2.4-plugin-accept.md` の先行診断も同一の限界を持つ。

**結論（5.6 節）**: 上記 1〜5 はいずれも host contention ノイズ説を積極的に
反証するものではないが、対称的に、隔離環境（他プロセス不在を機械的に保証
できる環境）での再計測なしにこの説を採用し機械判定 FAIL を覆す根拠にする
こともできない。したがって本レポートでは非退行の断定を避け、6 節のとおり
判定不能として記録する。

### 5.7 効果判定

- **見込み（設計文書 5.3 節）**: +5〜10%（alloc 回数ベースで N=10 時 27
  alloc/req → 定数 2 alloc/req への削減から見積もった見込み値）
- **実測（RPS ベース）**: before → after（5.5 節の 3 回目データセット）で
  core 側 RPS を比較すると、
  GET /health: 416858.52 → 420389.90（+0.85%）、GET /hello/{name}:
  428580.65 → 426598.58（-0.46%）、GET /users/{id}: 412181.41 →
  413165.70（+0.24%）、POST /echo: 410241.99 → 397253.89（-3.17%）。
  未特定のノイズ（外部 contention か計測自体の負荷変動かは 5.6 節のとおり
  切り分けられていない）が RPS にも重畳している可能性があり、試行間の
  ばらつきが大きく、この単純比較から P1 の効果を数%単位で切り出すことは
  できない。
- **未達の原因分析（受け入れ基準の必須要件）**: RPS ベースの単純比較では
  見込み +5〜10% を明確には確認できなかった。主要因は次の 2 点と考えられる:
  1. **未特定のノイズが RPS・p95 の両方に重畳している可能性**があり、
     P1 単独の効果を切り出すには本イシューの計測環境では S/N 比が
     不十分だった（5.6 節のとおりノイズの発生源は特定できていない）。
  2. **P1 の効果は alloc 回数の削減であり、本ベンチのボトルネックが
     alloc ではない可能性**: `core-bench` の 4 エンドポイントは応答本文が
     小さく（`/health` は固定文字列、`/hello/{name}` はテンプレート文字列
     等）、accept〜応答送出のパイプライン全体に対してヘッダ解析の alloc
     削減が占める割合が相対的に小さいと考えられる。設計文書 5.3 節も
     「実際の RPS 改善率は malloc 実装・OS・並行度に依存する」と明記して
     おり、alloc 回数の削減が RPS に線形に反映されるとは限らない。
  3. **バイナリサイズ比 0.7391（before/after 共通）はコアバイナリ自体の
     縮小を示す**が、これは P1 単独の効果というより #595〜#599（Phase 1
     改善、before 基準コミット `655b150` に既に含まれる）と #591/#592（P1）
     の累積効果であり、before/after 比較の対象外（両者に共通するため）。
- **未達自体は完遂判定を妨げないが原因記録は必須**という #593 の受け入れ基準
  （設計文書 8 節）に照らし、上記を原因分析として記録する。alloc 回数
  ベースでの効果（設計文書 5 節、N=10 で 27→2 alloc/req、既に実装時点
  #591/#592 で `crates/http/tests/alloc_count.rs` により機械検証済み）は
  本イシューのスコープ外の再測定であり、#593 は「効果見込みからの実測差異
  の記録」を主眼とする。

特性」かを確定するため、適用前コミット `dfca2b8` の worktree で同一の
`FAIL_RETRIES=1 bash benches/bench-accept-exclusive.sh` を実行した

2. **p95: ツリー起因の退行の証拠なし**。9.2〜9.3 節で悪化方向に見えた
   /health・/hello は交互測定では改善方向（-7.9% / -6.3%）で再現せず、
   悪化方向を示した /users（+7.4%）・/echo（+5.3%）もペア間変動
   （±20% 超）と外部負荷混入の記録から系統的な差と断定できない
3. ただし **±10% 未満の p95 差は本ホストの測定精度では分離不能**であり、
   厳密な非退行の証明には他プロセスを排除した隔離ホストが必要。残余
   不確かさは週次ベンチ（`bench-schedule.yml`、`FAIL_RETRIES=1`）の
   継続監視で追跡し、系統的な悪化が続く場合は再調査する（#594 の
   スコープに接続）

#593 の受け入れ基準「REQ-1/NFR-1 の既存受け入れ基準に非退行」に対する
最終判定は「**退行の証拠なし（RPS・p99 等は非退行確認済み、p95 は測定
精度の範囲内で差を検出せず）**」とする。実測値・機械判定（FAIL）は
一切改変せず本レポートに全て記録した。

交互測定の生データ（48 JSON・loadavg ログ・計測スクリプト）は実行
セッションの scratchpad に保存した（一時領域のため恒久保存はしない。
再現手順は本節記載のプロトコルどおり）。

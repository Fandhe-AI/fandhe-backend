# イシュー #594: 性能改善ツリー #579 全適用後の専有ベンチ総括と退行検知への組み込み

対象: 性能改善ツリー #579（Phase 1 = #583〜#587、Phase 2 = #588/#589 設計判断、
Phase 3 = #590〜#593、P1 ヘッダゼロコピー化）を全適用した現 main 先端の総括。
比較コミット: pretree（ツリー適用前）= `dfca2b8`（#593 9.4〜9.6 節と同一）/
current（ツリー適用後）= `2d642f8`（origin/main 先端）。

## 0. 結論

- **前後比較**: RPS・p99・RSS・バイナリサイズ・起動時間の非退行は `benches/reports/
  issue593-p1-zero-copy-bench.md`（以下「#593 レポート」）9 節が P1 区間限定・
  外部負荷機械検証付きで既に確定済み（±2.1% 以内）。本イシューは追加で
  **p50・CPU 消費（リクエストあたり）・#579 プロトコル整合の c=64 絶対値**を
  新規計測し（1〜3 節）、CPU 非悪化を確認した（4 節）。ツリー全体
  （pretree=`dfca2b8` → current=`2d642f8`）を #593 9.7 節と同一の外部負荷
  機械検証付き交互測定で再確認する作業は本イシューでは実施していない
  （5.3 節に理由と限界を明記）。
- **目標達成度**: #579 目標「hyper 素実装同等（約 35 万 RPS、axum-ref比 +8〜15%）」
  に対し、c=64・#579 プロトコル整合条件での実測は GET /health で
  **345,497 RPS（axum-ref 比 +4.66%）**、他 3 エンドポイントは axum-ref比
  +0.7%〜+5.8%（6 節）。絶対値は #579 記録値（31.7 万 RPS）を上回るが、
  axum-ref 比での目標 +8〜15% には届いていない。#593 5.7 節・9.4 節の
  逐次比較が示すとおりツリーの RPS 寄与自体が測定分解能未満（cur/pretree
  比 0.977〜1.012）であるため、この達成度はツリー適用**前から**概ね
  axum-ref 同等以上だったことを示すものであり、ツリーの新規貢献としての
  +8〜15% ではない（6 節で原因を分析）。
- **CPU・メモリ非悪化**: リクエストあたり CPU 消費は core（0.007586 ms/req）が
  axum-ref（0.009078 ms/req）比 **0.8356（-16.4%）** で悪化なし（4 節）。
  RSS は #593 9.2/9.3 節（アイドル比 0.90〜0.91、負荷時は core が axum-ref
  より一貫して小さい）を踏襲し悪化なし。
- **週次ベンチへの反映**: `bench-schedule.yml` は現行のまま main 先端を
  継続計測しており追加の接続作業は不要と判断する。p95 基準運用見直しは
  別課題として起票案を 8 節に記載する（承認待ち、本 PR では起票しない）。

## 5. 交互ペア測定（外部負荷機械検証付き）の扱い

### 5.1 既存の確定測定（#593 レポート 9.7 節、再掲）

#593 の評価区間（before=`655b150` / after=`1aeda06`、P1 区間限定）について、
外部 CPU 占有率を窓単位で機械検証したうえでの交互測定が既に実施済み・確定して
いる。

- 採用 64 窓の外部 CPU 占有率: 中央 0.73% / 最大 2.45%、汚染窓 0 件
- p95 中央値比（cur/pre）: GET /health +1.4%・GET /hello/bench -1.4%・
  GET /users/42 -2.1%・POST /echo -1.2%（いずれも ±2.1% 以内、系統的傾向なし）
- **判定: P1 区間の非退行を確認**（詳細は #593 レポート 9.7 節参照）

### 5.2 ツリー全体（pretree=`dfca2b8` → current）の交互測定（#593 9.6 節、参考値）

#593 9.6 節は pretree=`dfca2b8` / cur=`823ce73`（現 current とバイナリ等価）の
core-bench 同士を交互 6 ペアで比較したが、外部負荷の**窓中**検証を伴わない
（セッション開始前の loadavg 確認のみ）。結果は p95 比で GET /users/42 +7.4%・
POST /echo +5.3% と名目しきい値（5%）を超過する値を含むが、#593 レポートは
「9.7 節（外部負荷機械検証あり）で ±8% 級のばらつきが ±2.1% 以内に収束した
ことから、9.6 節の超過は外部負荷ノイズだった可能性が高い」と結論している
（ただし 9.6 節自体は「ツリー全体」区間であり P1 区間限定の 9.7 節とは対象が
異なる点に注意）。

### 5.3 本イシューでの追加実施なしとその理由

**ツリー全体（`dfca2b8` → `2d642f8`）を 9.7 節と同一プロトコル（外部負荷
機械検証付き交互測定、16 セッション × 4 エンドポイント）で再実施することは
本イシューでは行わなかった**。理由:

1. 該当プロトコルは #593 9.7 節時点でも 1 回のセッション中断・再実行を要する
   規模（16 セッション逐次、約 1 時間規模）であり、本イシューはレポート総括・
   目標達成度分析・週次ベンチ判断が主眼で、同規模の追加計測は受け入れ基準
   「達成度と残差原因の明記」に対して限界的な追加価値と判断した
2. pretree 側バイナリの再ビルドに一時 worktree（`git worktree add`）を要するが、
   本セッションの実行環境（隔離 worktree・サンドボックス）では worktree 外の
   ディレクトリでの `cargo build` 実行が阻害され、追加の pretree 絶対値計測
   （3 節相当を pretree 側でも取得する試み）を完遂できなかった
3. 4 節（CPU 計測）実施中に自プロセス負荷で loadavg1 が 5.47 まで上昇して
   おり（1 節）、この状態から追加で長時間の交互測定へ進んでも #593 9.1 節が
   記録したような外れ値混入リスクがあり、精度の高い追加確定測定には別途
   静穏ホストでのセッションを要する

**この限界を隠さず記録する**: ツリー全体の非退行確定は、P1 区間（Phase 3、
#593 9.7 節、外部負荷機械検証付き・確定）+ Phase 1 区間（`dfca2b8`→`655b150`、
#593 9.4 節の軽量逐次比較、系統的退行なし・自己変動幅と同程度）の**合成**に
留まり、ツリー全体を単一の外部負荷機械検証付き交互測定で直接確認したもの
ではない。両区間とも個別には非退行の証拠があるため合成結論として「ツリー
全体で系統的な退行はない」と判断するが、9.7 節と同精度の直接確認ではない
点を明記する（フェイルクローズ、実測範囲を過大に主張しない）。

## 6. 目標達成度と残差原因の分析

### 6.1 達成度

- **絶対値目標（hyper 素実装同等 ≈ 35 万 RPS）**: c=64・GET /health で
  345,497 RPS を記録し、目標水準に到達（2 節）。ただし hyper 素実装自体は
  本リポジトリに存在せず本イシューでは再計測していない（本フレームワークの
  `core-bench`（フル機能スタック経由）が hyper 直接叩きにどこまで近い数値を
  出せるかという意味での目標であり、hyper 単体の再測定は #579 一次ソースに
  留める）
- **相対値目標（axum-ref 比 +8〜15%）**: c=64 では +0.48%〜+5.15%（2 節）、
  c=128・P1 区間確定測定では ±2.1% 以内（5.1 節）。**目標 +8〜15% には
  未達**
- バイナリサイズ縮小（1,384,872B → 1,023,576B、比 0.7391、-26.1%）は
  ツリー全体を通じて一貫して確認済みの成果

### 6.2 未達の原因分析（受け入れ基準の必須要件）

#593 レポート 5.7 節・9.7 節の分析を踏襲し、以下を残差原因として記録する。

1. **ツリーの RPS 寄与自体が測定分解能未満**: #593 9.4 節の 3 コミット逐次
   比較（`dfca2b8` → `655b150` → `823ce73`）は cur/pretree 比 0.961〜1.012
   で、対照群の自己変動幅（0.99〜1.03）と同程度であり系統的改善を検出でき
   なかった。9.7 節の P1 区間限定・外部負荷機械検証付き確定測定でも
   cur/pre 比 0.980〜1.014（±2.1% 以内）で、有意な改善は確認できていない
2. **ボトルネックが alloc ではない可能性**（#593 5.7 節）: P1（ヘッダ
   ゼロコピー化）は 1 リクエストあたりの alloc を N=10 ヘッダで 27→2 へ
   削減する設計だが（`crates/http/tests/alloc_count.rs` で機械検証済み）、
   `core-bench` の 4 エンドポイントは応答本文が小さく、accept〜応答送出の
   パイプライン全体に対して alloc 削減が占める割合が相対的に小さいと
   考えられる
3. **actix/ntex 帯（約 54 万 RPS）到達には構造的な変更が必要**
   （`docs/design/per-core-runtime-decision.md`）: 軸 A（`SO_REUSEPORT` +
   コアごとの accept 経路）+ 軸 B（ハンドラの `!Send` 許容）の一般形は
   13 公開クレートの breaking change に波及するため不採用と判断済み
   （イシュー #589）。現行の「最小コア + 4 拡張点 trait」設計を維持する
   限り、この構造差が axum-ref 比 +8〜15% を上回る改善の天井になっている
   可能性が高い
4. c=64 条件では axum-ref 比が上振れする（2 節、+0.48%〜+5.15%）一方、
   c=128 の P1 区間確定測定では ±2.1% 以内に収束する（5.1 節）。接続数に
   応じて相対差が変動する現象自体もこの分析からは完全には切り分けられて
   おらず、断定を避ける

未達自体は #594/#593 の受け入れ基準（達成度と残差原因の明記）を妨げない。
alloc 回数ベースの効果（設計文書 5 節、既に #591/#592 実装時点で機械検証済み）
は本イシューのスコープ外の再測定とする（#593 と同一整理）。

## 7. 多フレームワーク比較の再現手順（#579 プロトコルの恒久記録）

一次ソースは #579 本文（2026-08-11 起点、15 フレームワーク横断比較）。
本リポジトリに実在する対象（axum-ref・core-bench）についての再現手順を
以下に恒久記録する。外部フレームワーク（hyper 素実装・actix-web・ntex 等）
は本リポジトリに存在しないため比較値の一次ソースは #579 のまま、条件の
記録に留める。

### 7.1 前提

- ツール: `oha` 1.15.0（`cargo install oha` または配布バイナリ。バージョン
  固定で導入し勝手に自動更新しない）
- ホスト: 12 コア以上を推奨（本レポート計測環境）、専有実行（他プロセスの
  CPU 消費が最小の状態、`benches/lib/exclusive.sh` の静穏確認 `LOAD1_MAX`
  相当の基準）

### 7.2 ビルド

```bash
cargo build --release --bin axum-ref
cargo build --release --example core-bench -p fandhe-backend-core
```

### 7.3 実行・計測

```bash
# axum-ref（baseline）
BIND_ADDR=127.0.0.1:3001 ./target/release/axum-ref &
oha -z 3s -c 64 --no-tui --output-format json http://127.0.0.1:3001/health >/dev/null  # warmup
oha -z 15s -c 64 --no-tui --output-format json http://127.0.0.1:3001/health

# core-bench（現 main 先端）
BIND_ADDR=127.0.0.1:3001 ./target/release/examples/core-bench &
oha -z 3s -c 64 --no-tui --output-format json http://127.0.0.1:3001/health >/dev/null  # warmup
oha -z 15s -c 64 --no-tui --output-format json http://127.0.0.1:3001/health
```

または `benches/bench-http.sh` を使い複数回・中央値評価する:

```bash
RUNS=5 DURATION=5s CONNECTIONS=64 TARGET_BIN=./target/release/examples/core-bench \
  bash benches/bench-http.sh
```

- 対象エンドポイント: `GET /health`・`GET /hello/{name}`・`GET /users/{id}`・
  `POST /echo`（4 種、`benches/bench-http.sh` 固定定義）
- 接続数: #579 整合は `c=64`、本リポジトリの公式ハーネス（`bench-accept-
  exclusive.sh`）整合は `c=128`
- 評価: 3〜5 回中央値（`benches/README.md` の中央値評価規約）
- 外部フレームワーク（hyper 素実装・actix-web・ntex 等）との比較値は

## 8. 週次ベンチ（`bench-schedule.yml`）への反映要否判断

### 8.1 判断: 現行のまま維持（追加接続作業は不要）

`.github/workflows/bench-schedule.yml` は `benches/bench-accept-exclusive.sh`
（`FAIL_RETRIES=1`）を週次・`workflow_dispatch` で main 先端に対して実行する
既存構成であり、対象バイナリは常にツリー適用後（かつ以降の変更も含む）の
main 先端になる。ツリー適用という一過性のイベントに対応するための追加の
接続作業（対象コミットの固定化等）は不要と判断する。

### 8.2 p95 基準運用の見直し（起票案、承認待ち）

#593 レポート 9.5 節が申し送った「p95 <= 1.10（axum-ref 比）基準は、本
ホスト + c=128 条件ではツリーと無関係に PASS/FAIL 境界で不安定（ツリー
適用前コミット `dfca2b8` でも同一ホストで再現する p95 超過を観測）」という
所見は、週次ベンチが実行される `ubuntu-latest`（ホステッドランナー、
[[ci]]）には**そのまま当てはまらない**（ローカル専有ホストと
ubuntu-latest はスペック・ノイズ特性が異なるため）。したがって系統的な
悪化があるかどうかは週次ベンチの継続実行結果そのもので判断すべきであり、
本イシュー単体でホステッドランナー側の基準緩和・強化を断定する根拠はない。

一方で、ローカル専有ホストでの p95 基準運用（マージン・試行回数・ホスト
要件）に既知の不安定性がある事実は記録として残っており、以下を改善提案
候補として記録する（[[out-of-scope-tracking]] に従い、**本 PR ではユーザー
承認前提のため起票しない**。起票案の骨子のみ記録し、承認後に別途起票する）。

- **起票案タイトル案**: `bench: 専有ハーネスの p95 基準（axum-ref 比 <=
  1.10、c=128）の運用見直しを検討する`
- **本文骨子**: #593 9.5 節・本レポート 5 節の実測（ツリー適用前後どちらの
  コミットでも同一ホスト・c=128 条件で p95 超過が再現する）を根拠に、
  マージン（1.10 → 1.15 等）・試行回数（`FAIL_RETRIES` の見直し）・
  評価接続数（c=128 → 別条件）のいずれかまたは組み合わせでの緩和・
  安定化を検討する。ホステッドランナー（週次ベンチ）側への直接適用は
  慎重に判断し、ローカル専有計測の運用規約（`benches/README.md`）改定を
  主眼とする
- **リスク**: 対応しない場合、ローカル計測での p95 FAIL が今後も特定
  エンドポイントによらず散発し、真の退行との判別コストが継続する。
  対応する場合、基準を過度に緩めると実際の退行を見逃すリスクがあるため
  変更幅は慎重に検討する必要がある
